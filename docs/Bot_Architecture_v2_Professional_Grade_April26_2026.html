01

Why this document exists, and what changed from v1

The audit (Phases 1–6 in the synthesis document) identified a system that worked but was fragile, hard to extend, and silently broken in several places. The first architecture document recommended a modular monolith — one Python codebase, cleanly organized, fast to build. You read it and pushed back: not enough ambition. You wanted "as close to hedge fund grade as possible." Personnel is not a constraint, time is not a constraint, the goal is a serious system that can grow into something complex, strong, and profitable.

That changes the recommendation entirely. This document discards the modular monolith and replaces it with what professional shops actually build: a multi-service distributed architecture with proper separation of concerns, a real message bus, separate databases per service domain, a full observability stack, and a deployment story that supports independent service updates without taking the system down. We're going to use the same vocabulary professional firms use — OMS, EMS, Risk Engine, Portfolio Management Service — because those names map onto well-understood responsibilities, and using them anchors the design in patterns that have been proven at scale.

What you get out of this document:

  • A serious architectural design you can actually build, with names and choices you can defend
  • The specific technologies (NATS JetStream, PostgreSQL, Kubernetes, the LGTM observability stack) and why each was chosen over alternatives
  • End-to-end scenarios that show how the system behaves when things go right and when they go wrong
  • A migration roadmap that doesn't pretend this is a weekend project
  • Honest acknowledgment of where we deliberately stop short of true hedge fund infrastructure, and why
02

What hedge funds actually do — and what we'll borrow

Before designing anything, it's worth grounding ourselves in what professional quant operations actually look like. The vocabulary and patterns matter because they encode decades of hard-won lessons about what breaks at scale.

The canonical six-component structure

Every serious quant trading firm — from Citadel and Two Sigma down to mid-sized prop shops — separates their trading systems into roughly six layers:

LayerOne-line responsibilityWhy it's separate
Data EngineIngest market data, normalize, distribute to consumersMarket data is high-volume, latency-sensitive, used by many downstream consumers. Co-locating it with strategy logic creates contention.
Strategy EngineTransform data into trade signals and position intentionsStrategies fail. Strategies get changed often. Isolating them prevents one buggy strategy from affecting others.
Risk EngineReal-time pre-trade and post-trade risk checks; limits enforcementRisk is the firm's last line of defense. It must be impossible to bypass. Centralizing it ensures every order goes through the same rules.
Order Management System (OMS)Authoritative record of all orders. Lifecycle, state transitions, reconciliation.The OMS is the system of record. It must be correct even when other components fail. Reconciliation against the broker happens here.
Execution Management System (EMS)Routes approved orders to venues. Handles fills, partial fills, cancellations, retries.Venue connectivity is messy. Each venue has its own quirks, rate limits, error semantics. Encapsulating that prevents the rest of the system from caring.
Portfolio Management System (PMS)Maintains current positions, computes P&L, provides state to other components."What do we own and what is it worth right now" is a question many components ask. One source of truth. P&L attribution lives here.

Acadian Asset Management's Multi-Strategy fund describes this as "sleeves operating almost independently" with a "centralized risk management" layer that "considers buying power and cashflows" and has "real-time sight of proposed trades, and aggregates risk to control them." That's exactly the OMS/Risk/PMS pattern.

Quantifi (a hedge fund tech vendor used by professional firms) explicitly describes its platform as "microservices architecture built up of single-purpose components allowing functionality to be consumed in ways applicable to your unique business requirements." Same idea. Single-purpose services, message bus between them.

The hedge fund quality bar — what makes their systems professional

Beyond the architectural shape, four things distinguish professional trading systems from hobby projects:

  • Determinism. Run the same inputs, get the same outputs. Replay any decision the system made, exactly. NautilusTrader explicitly designs for this with their "deterministic time model" running across both research and live.
  • Auditability. Every order, every state transition, every risk check is recorded with the inputs and outputs. You can answer "why did we make this trade at 11:47 last Tuesday" months later, with the actual reasoning.
  • Testability under failure. What happens when Kalshi rate-limits us? When Claude returns malformed JSON? When the database is briefly unreachable? Every failure mode has a defined behavior, not "it crashes and we figure it out."
  • Research-to-live parity. Strategies developed in research run unmodified in production. No "this works in paper but not in live" surprises. Same code, same execution semantics, just different config.

What we will borrow

  • The six-layer separation — Data, Strategy, Risk, OMS, EMS, PMS. Each as its own service.
  • Event-driven communication via a message bus — services publish events, other services subscribe. No direct calls.
  • Event sourcing for the OMS and PMS — the order log and the position log are the source of truth. Current state is derived.
  • Strict schema versioning — events have versions. Adding a field doesn't break old consumers. Removing one is a deliberate process.
  • Research-to-live parity via mode toggle — same services, different config, different venue adapter. Borrowed directly from Nautilus and Freqtrade.
  • Full observability stack — metrics, logs, traces. Every event in the system observable end-to-end.
  • Deterministic replay — record every input event, every output event. Replay any historical decision deterministically.

What we will deliberately not adopt

Hedge funds at the top tier do things we genuinely do not need:

  • Co-located servers / kernel bypass / FPGA execution. Latency at microsecond scale is irrelevant for prediction markets that resolve in days or weeks. Our latency target is "place orders within 100ms of decision," which is millions of times slower than HFT.
  • In-house pricing libraries for exotic derivatives. Kalshi binary contracts are trivially priced. We do not need our own Black-Scholes implementation.
  • Compliance, regulatory, and audit reporting infrastructure. We are individuals trading our own capital. The regulatory surface is small.
  • Multi-tenant architecture. One firm, two users. We do not need RBAC for hundreds of traders.
  • Dedicated SRE / DevOps personnel. Peter and Filippo will do everything. Architecture choices reflect this — we use managed services where possible to reduce operational load.

Section 12 expands on each of these.

What's important about this picture

  • Every service has one job. No service does multiple things. Strategy services propose orders, they don't place them. Risk service approves orders, it doesn't execute them. EMS executes, it doesn't decide.
  • Services never call each other directly. All communication is through NATS. This is the single most important rule. It means a service can be restarted, replaced, or have a new version deployed without anyone else needing to know.
  • State lives in the event log. The OMS and PMS are event-sourced — their PostgreSQL databases store every event that ever happened. Current state is computed from the events. This makes the Phase 2 audit bug ("bankroll only goes up") structurally impossible.
  • Adapters wrap the messy outside world. Every external API has its own adapter that translates the venue's quirks into our clean internal event schema. A change at Kalshi only affects the Kalshi adapter.
  • Observability is cross-cutting. Every service emits metrics, logs, and distributed traces. Every event flowing through NATS can be traced end-to-end. When something breaks at 2 AM, you can see exactly where.
The mental model. Imagine each service as a person in a small office, each with a specific job, communicating only by leaving notes on a central message board (NATS). The OMS clerk maintains the master ledger. The Risk officer reviews every proposed trade before approving it. The EMS trader executes approved trades. The PMS accountant tracks positions and P&L. They don't share a brain — they share a notice board. If the trader is out sick, the office still functions: orders pile up on the notice board for them to handle when they return. If the Risk officer is replaced, nothing else changes.
04

The eight services, named and explained

Eight independently-deployable services. Each runs in its own Docker container, has its own configuration, its own logs, its own metrics, and (where applicable) its own database. They communicate only through NATS.

data-svc
role: data ingestion · language: Python · state: stateless (caches in memory) · scale: 1 replica

Owns all communication with the outside world for data acquisition. Wraps Kalshi market data, Polymarket data, FRED economic indicators, news APIs, and Anthropic Claude calls for AI edge detection. Each external system has its own adapter file. The service publishes typed events to NATS subjects.

Subjects published
  • market.tick.kalshi.<ticker> — price updates
  • market.state.<ticker> — status changes (open, closed, settled)
  • data.fundamental.fred.<series> — FRED data updates
  • data.research.edge.<ticker> — AI-generated edge analysis (Claude output)
  • data.news.<ticker> — news/sentiment hits
Why isolated

External APIs change, fail, rate-limit. By isolating all external calls in one service, the rest of the system never sees a Kalshi outage as anything other than a paused stream of market.tick events. Strategies don't break when an API does. The service has its own retry logic, circuit breakers, and per-source health metrics.

strategy-* (one per strategy)
role: signal generation · language: Python · state: stateless · scale: N replicas (one per strategy)

Each strategy is its own service. strategy-timely, strategy-midsel, strategy-arb, plus any new strategies we add. Each one subscribes to the data events it cares about, applies its logic, and publishes order.proposed.* events when it wants to bet.

Subjects subscribed
  • market.tick.>, market.state.> — from data-svc
  • data.research.edge.> — AI edge analysis
  • portfolio.updated — from pms-svc, so strategy knows current bankroll/positions
Subjects published
  • order.proposed.<strategy_name> — "I want to place this bet"
  • strategy.heartbeat.<strategy_name> — periodic alive signal
  • strategy.skipped.<strategy_name> — markets it evaluated but chose not to bet, with reason
Why one service per strategy

This is a deliberate design choice. Strategies fail more than any other component. Strategies need to be modified often. Strategies are added, removed, A/B tested. Putting each in its own service gives you: independent deployment, independent scaling, independent failure isolation, easy A/B testing (run two versions of TIMELY simultaneously with different parameters). Adding a new strategy is a new pod, not a code change to a shared file.

risk-svc
role: pre-trade risk checks · language: Python · state: reads portfolio state from pms-svc · scale: 1 replica (HA optional)

The single point through which every proposed order must pass. Implements all gates in one place: status checks, weekly loss limits, exposure caps (per-ticker, per-category, total), contradictory position checks, ticker concentration, sizing logic. Owns the half-Kelly / Bayesian-Kelly sizing calculation.

Subjects subscribed
  • order.proposed.> — from any strategy service
  • portfolio.updated — from pms-svc
  • risk.limits.update — manual updates to risk parameters
Subjects published
  • order.approved.<strategy_name> — with sized amount
  • order.rejected.<strategy_name> — with reason
  • risk.alert.<type> — threshold breaches, anomalies
Why isolated

Risk is the firm's last line of defense against catastrophic loss. Centralizing it ensures every order goes through the same rules. If risk-svc is down, no orders fire — the system fails closed. If you want to change a risk rule, you change it in one place. If you need to audit "why was this trade approved at $X size," the answer is in this service's logs.

oms-svc — Order Management System
role: authoritative record of all orders · language: Python · state: PostgreSQL (event-sourced) · scale: 1 replica

The system of record for orders. Subscribes to order.approved.*, persists each one to its event log, assigns it an order ID, transitions it through states (NEW → SUBMITTED → ACKNOWLEDGED → PARTIALLY_FILLED → FILLED / CANCELLED / REJECTED), and exposes the order book to the rest of the system. Reconciliation against venues happens here.

Subjects subscribed
  • order.approved.> — from risk-svc
  • order.acknowledged, order.filled, order.rejected — from ems-svc
Subjects published
  • order.submitted.<order_id> — signals ems-svc to actually execute
  • order.state.changed.<order_id> — lifecycle transitions
Database

PostgreSQL, append-only orders table with full event log. Every state transition is a row. Order's current state is computed from its history. Daily reconciliation job pulls Kalshi's order/fill records and compares against the local log; mismatches trigger alerts and auto-correction events.

ems-svc — Execution Management System
role: execute orders on venues · language: Python · state: stateless · scale: 1 replica per venue (or per mode)

Talks to Kalshi (and eventually Polymarket) to actually place orders. Has two modes controlled by config: live (real orders) and paper (simulated fills against current market prices). The same service binary, different config, different output stream. This is the Freqtrade --dry-run pattern, but at the service level.

Subjects subscribed
  • order.submitted.> — from oms-svc
Subjects published
  • order.acknowledged.<order_id> — venue accepted
  • order.filled.<order_id> — with fill details
  • order.rejected.<order_id> — venue rejected, with reason
  • venue.status.<venue> — venue health (rate-limited, down, etc.)
Why two modes

Paper mode is what becomes our shadow bot. Same code, same logic, no real orders. Section 09 details how this replaces the old shadow_bot.py.

pms-svc — Portfolio Management System
role: positions, P&L, bankroll · language: Python · state: PostgreSQL (event-sourced) · scale: 1 replica

The authoritative state of "what we own and what is it worth." Subscribes to filled orders, market price updates, and resolution events. Maintains an event-sourced ledger of every change to positions and bankroll. Computes current state on demand. Calculates P&L by strategy, category, time period.

Subjects subscribed
  • order.filled.> — from ems-svc
  • market.tick.> — from data-svc, for mark-to-market
  • market.state.settled.> — from data-svc, for resolution P&L
  • deposit.recorded, withdrawal.recorded — manual events
Subjects published
  • portfolio.updated — current bankroll, positions, exposures
  • portfolio.reconciliation.alert — if drift detected vs venue truth
  • pnl.realized.<strategy>.<category> — P&L attribution events
Why event-sourced

This directly fixes the Phase 2 audit bug. There is no "current bankroll" field stored anywhere. Bankroll is computed by replaying the event log: starting balance + every deposit + every win − every loss − every withdrawal. You cannot have a "loss path that doesn't decrement" because there is no decrement code path — there is just an event stream and a replay function. If you ever need to fix a historical error, you append a corrective event — you never edit history.

reporting-svc
role: dashboards, daily/weekly reports, learning analytics · language: Python · state: read-only consumer · scale: 1 replica

Consumes events from across the bus and produces human-readable outputs: daily summary, weekly P&L, strategy performance attribution, learning multiplier reports, shadow vs live comparison. Pure read-only consumer. Generates HTML reports that are sent via Telegram or stored for the web dashboard.

Why isolated

Reports break, run slow, change format often. Isolating them means a slow report doesn't slow down the trading path. A bug in report formatting doesn't risk financial damage.

telegram-svc
role: human interface · language: Python · state: stateless · scale: 1 replica

The user interface for Filippo and Peter. Subscribes to events that humans care about (order placements, large losses, status changes, daily reports) and pushes them to Telegram. Receives commands from humans (/portfolio, /pause, /multipliers) and translates them into events on the bus.

Crucially: telegram-svc contains no business logic. It just translates events ↔ humans. /pause publishes a system.pause.requested event. The risk service handles it. This separation means breaking Telegram never breaks trading.

mcp-svc — Model Context Protocol server
role: AI agent integration · language: Python (FastAPI + MCP SDK) · state: stateless · scale: 1 replica

Exposes the bot as an MCP-compatible server. Claude in any chat can connect to this and query state, run reports, simulate bets, even (with auth) trigger pauses or strategy toggles. Section 10 details the tool surface.

This is also where the future "external MCPs the bot consumes" connector lives — if you connect an MCP tool that provides news data or a polling aggregator, mcp-svc handles the integration.

Service count rationale. Eight is deliberate. Fewer would mean conflating responsibilities (e.g. merging risk into OMS would put the firm's last line of defense in the same blast radius as order tracking). More would mean operational overhead without benefit (e.g. splitting "data-svc" into one service per data source means 5 deploys when we add a new market data field). The split here matches the canonical hedge fund layers, with two additions (telegram, mcp) that are external interfaces rather than core trading logic.
05

The message bus — NATS JetStream and event contracts

Why NATS JetStream

This is one of the most important technical choices. The candidates were Apache Kafka, Redis Streams, and NATS JetStream. Here is the honest comparison for our specific situation:

KafkaRedis StreamsNATS JetStream
Throughput at our scaleMore than enoughMore than enoughMore than enough
p99 latency~12ms~0.8ms~3ms
Operational complexityHigh (ZooKeeper / KRaft)Medium (memory-bound)Low (single binary)
Persistence / replayExcellent, weeks of retentionMemory-boundDisk-backed, replayable
Subject hierarchy filteringTopic-basedPer-streamHierarchical (e.g. order.>)
Best fit forMassive event pipelines, log aggregationIf you already run RedisMicroservice messaging at our scale

NATS JetStream wins clearly for our scenario. Kafka is overkill — we are not LinkedIn. Redis Streams is fine but memory-bound and has weaker replay. NATS gives us: (1) the operational simplicity of a single Go binary, (2) durable persistent streams for replay, (3) hierarchical subject filtering that makes our event taxonomy elegant, (4) at-least-once delivery semantics, (5) sub-5ms latency which is faster than we need.

A 2026 industry consensus: "NATS JetStream combines Kafka-like persistence with Redis-like simplicity. It's the best choice for microservice communication." For a two-person team running serious infrastructure, this is the right level of operational burden.

Subject taxonomy

NATS uses subject hierarchies with dot-separated tokens. Our taxonomy:

market.tick.<venue>.<ticker> # price update market.state.<ticker>.<state> # open / closed / settled market.fill.<venue>.<ticker> # trade tick from venue data.fundamental.<source>.<series> # FRED data, etc. data.research.edge.<ticker> # AI edge analysis output data.news.<ticker> # news/sentiment order.proposed.<strategy> # strategy wants to bet order.approved.<strategy> # risk approved + sized order.rejected.<strategy> # risk or venue rejected order.submitted.<order_id> # OMS told EMS to execute order.acknowledged.<order_id> # venue acked order.filled.<order_id> # filled (full or partial) order.cancelled.<order_id> # cancelled order.state.changed.<order_id> # OMS lifecycle transition portfolio.updated # PMS state change portfolio.reconciliation.alert # drift detected pnl.realized.<strategy>.<category> # P&L attribution event risk.alert.<type> # threshold breach strategy.heartbeat.<strategy> # strategy alive strategy.skipped.<strategy> # market evaluated, skipped system.pause.requested # human-initiated pause system.resume.requested system.shutdown.requested venue.status.<venue> # venue health

Event schemas — strictly versioned

Every event is a JSON object with a strict schema. We use JSON Schema for validation and Pydantic models in Python. Every event has these required fields:

{ "event_id": "uuid", # unique per event "event_type": "order.proposed", # matches subject hierarchy "event_version": "v1", # schema version "emitted_at": "2026-04-26T14:30:00Z", # UTC ISO 8601 "emitted_by": "strategy-timely", # service that emitted "correlation_id": "uuid", # traces a flow across services "payload": { ... } # type-specific data }

The correlation_id is critical. When a strategy proposes an order, it generates a correlation_id. Every downstream event triggered by that proposal (the risk approval, the OMS submission, the EMS fill, the PMS update) carries the same correlation_id. This is what lets distributed tracing in Tempo show you "the journey of this one bet from idea to fill" as a single trace.

Schema evolution rules

  • Adding a new optional field — allowed in any version. Old consumers ignore it.
  • Adding a new event type — allowed. Old services don't subscribe to it.
  • Removing a field — never. Mark deprecated, leave in place.
  • Changing semantics of a field — requires version bump (v1 → v2). Both versions coexist for a deprecation period.
  • All events go through a schema registry — in our case, a shared Python package bot-events that every service imports. Version bumps require a PR.

Delivery guarantees

NATS JetStream provides at-least-once delivery with consumer acknowledgment. Every consumer service is responsible for being idempotent — processing the same event twice must not cause duplicate side effects. This is non-negotiable.

Idempotency is achieved by:

  • Every event has a unique event_id
  • Services keep a small ring buffer (in Redis or in-memory) of recently-processed event_ids
  • Database operations use upserts keyed on event_id, not blind inserts

Event sourcing in OMS and PMS

The two services that own truth (orders and positions) use event sourcing. Here's what that looks like concretely.

OMS event log table
CREATE TABLE order_events ( event_id UUID PRIMARY KEY, order_id UUID NOT NULL, event_type TEXT NOT NULL, -- 'created' | 'submitted' | 'acknowledged' | 'filled' | ... event_version TEXT NOT NULL, -- 'v1', 'v2', etc. emitted_at TIMESTAMPTZ NOT NULL, correlation_id UUID, payload JSONB NOT NULL -- the event data ); CREATE INDEX ix_order_events_order_id ON order_events(order_id, emitted_at);

Every order's full history is the sequence of rows with that order_id, ordered by time. The order's current state is computed by replaying its events:

def get_order_state(order_id): events = db.query("SELECT * FROM order_events WHERE order_id = ? ORDER BY emitted_at", order_id) state = {"status": "NEW", "filled_qty": 0, "remaining_qty": 0} for e in events: state = apply_event(state, e) return state
PMS event log table

Identical pattern, but for portfolio events:

CREATE TABLE portfolio_events ( event_id UUID PRIMARY KEY, event_type TEXT NOT NULL, -- 'deposit' | 'withdrawal' | 'bet_placed' | 'bet_won' | 'bet_lost' | 'mark_to_market' event_version TEXT NOT NULL, emitted_at TIMESTAMPTZ NOT NULL, correlation_id UUID, payload JSONB NOT NULL ); CREATE INDEX ix_portfolio_events_emitted ON portfolio_events(emitted_at);

To compute current bankroll: SELECT SUM(payload->'delta_usd') FROM portfolio_events — and you have an audit-perfect bankroll figure that cannot be wrong because every change is in the table. The audit's Phase 2 finding ("bankroll only goes up because there's no decrement code") is structurally impossible here. Decrement events are just events with negative deltas.

Projections — the read side

Replaying the full event log every time someone asks for current state is wasteful. We use projections: materialized read models updated as events flow in.

  • Current positions projection — updated on every bet_placed / bet_won / bet_lost. Fast lookup of "do we own this ticker."
  • Bankroll projection — updated on every event. Single-row table with current total.
  • P&L by strategy projection — updated on resolution events. Per-strategy P&L summary.
  • Open orders projection — updated on order events. Snapshot of all orders not yet finalized.

Projections are derived. They can be wiped and rebuilt from the event log at any time. This is the magic of event sourcing — if you find a bug in your bankroll calculation, you fix the projection logic, run a one-time replay, and the new projection reflects reality. The events themselves are immutable history.

Reconciliation — closing the loop with venues

Once a day, oms-svc and pms-svc each run a reconciliation job:

  • OMS reconciliation: pull all orders from Kalshi for the past 7 days. Compare to local order log. If anything is in Kalshi but not local, emit order.reconciliation.missing.local. If anything is local but not Kalshi, emit order.reconciliation.missing.venue. Either case is an alert.
  • PMS reconciliation: pull current balance and positions from Kalshi. Compute expected balance from local event log. If delta > threshold, emit portfolio.reconciliation.alert with the diff.

This is what was missing in the old bot. The audit found that reconciliation had run exactly once, manually, four days before the audit. In the new system, it runs automatically every day, and any drift is immediately visible.

The operational stack — Kubernetes, observability, secrets, CI/CD

Where everything runs — managed Kubernetes

For a serious distributed system on a two-person team, Kubernetes is the right answer in 2026 — provided you use a managed offering (EKS on AWS, GKE on GCP, or DigitalOcean Kubernetes) so you don't operate the control plane yourself. The 2026 industry consensus is clear: 92% of new container orchestration deploys are Kubernetes; Docker Swarm is stagnant and has known compatibility issues since Docker Engine v29.

Specifically: DigitalOcean Kubernetes (DOKS) is our recommendation. Reasons:

  • Free managed control plane — you only pay for worker nodes
  • Predictable pricing ($12/mo for a small worker, scales linearly)
  • Significantly simpler than AWS EKS or GCP GKE for a small operator
  • Includes managed PostgreSQL, managed Redis, load balancers, block storage — all the pieces we need
  • UK / EU regions available (preserves your VPN UK-routing requirement if needed)

Alternative for cost-sensitivity: Hetzner Cloud + self-managed K3s. ~$30/month total for a 3-node cluster. Trade-off is you operate the control plane. Reasonable for two technical people but more ops load.

The LGTM observability stack

Loki (logs) + Grafana (visualization) + Tempo (traces) + Mimir/Prometheus (metrics). This is the de facto modern open-source observability stack for distributed systems in 2026. All four projects are by Grafana Labs. They integrate seamlessly. Combined data flows:

  • Metrics — every service exposes /metrics in Prometheus format. Service-level metrics: orders/minute, edge detection latency, NATS publish rate. Business metrics: bankroll, open positions, daily P&L.
  • Logs — every service writes structured JSON logs to stdout. Loki ingests via Promtail, indexed by service + correlation_id.
  • Traces — OpenTelemetry SDK in every service. Every NATS publish/subscribe creates a span with the correlation_id. Tempo stores them. In Grafana, you see "the life of a bet" as a single trace spanning all 8 services.

What this gives you: when something breaks, you go to Grafana, find the metric anomaly, click into the relevant trace, see the full distributed call graph, and click into the logs of the specific service that failed. Total mean-time-to-diagnosis: minutes.

Secrets management

API keys, private keys, database credentials. Three options:

  • Kubernetes Secrets + sealed-secrets — minimal extra infrastructure. Secrets stored encrypted in git, decrypted by the cluster. Good enough for our scale.
  • HashiCorp Vault — the professional answer. Significant operational burden for our team size. Defer.
  • Cloud-native secret managers (AWS Secrets Manager, etc.) — if we were on AWS, the right answer. On DOKS, less seamless.

Recommendation: sealed-secrets. Encrypted secrets in git, decrypted in cluster. Good enough for a two-person team running their own money. Vault if we ever expand.

CI/CD pipeline

The deployment loop. What happens when Peter pushes a code change.

  1. Peter pushes a branch to GitHub. CI runs: linters, type checks, unit tests, integration tests against a local NATS + Postgres in the CI runner.
  2. Peter opens a PR. CI runs the same suite against the PR branch.
  3. Filippo (or Peter) reviews. Merge to main.
  4. On merge to main: GitHub Actions builds new Docker images for any changed service, tags with git SHA, pushes to a container registry (DigitalOcean's, or GHCR).
  5. Argo CD (running in the cluster) detects the new image tags via a sync loop. Compares to a separate deployments git repo that holds Kubernetes manifests.
  6. If we want auto-deploy: Argo applies the new image. Service rolls out (Kubernetes does rolling updates by default — old pods drained, new pods come up, no downtime).
  7. If we want manual approval (recommended for production): Argo waits for a human to click "sync" in the Argo UI.

Total deploy time from push-to-main to running in production: ~5 minutes if auto-deploy, ~5 minutes plus human latency if manual.

Three environments

Real engineering teams have three environments. Ours:

  • local — docker-compose on Peter or Filippo's laptop. Used for active development. Mock external APIs.
  • paper — trading-paper namespace in production cluster. Real external data, simulated execution. This is also the bot we run continuously to validate strategies. Replaces the old shadow_bot.py. Section 09 explains.
  • prod — trading-prod namespace. Live trading with real money.

Code change flow: develop in local, deploy to paper, observe for ≥3 days, then promote to prod. Promotion is a config change, not a code change — the same image runs in both, with different env vars.

Backup and disaster recovery

  • PostgreSQL: daily snapshots via DigitalOcean managed backup (7-day retention). Plus hourly logical backups to object storage (30-day retention).
  • NATS JetStream streams: replicated 3x within cluster. Stream contents replayed from PostgreSQL event logs in worst case.
  • Kubernetes manifests: in git. Cluster fully reproducible from kubectl apply -f.
  • Configuration: in git (with sealed secrets).
  • Recovery objective: rebuild full system from git + last DB backup in <1 hour. Tested quarterly.

Cost estimate

Realistic monthly running cost for this setup on DOKS:

  • Kubernetes worker nodes (3× small): ~$36
  • Managed PostgreSQL (1GB RAM, 10GB storage): ~$15
  • Managed Redis (1GB): ~$15
  • Load balancer: ~$12
  • Backups + object storage: ~$5
  • Container registry (free tier likely sufficient): $0
  • CloudFlare tunnel: $0 (free tier)
  • Anthropic API costs (Claude calls for edge detection): variable, est. $30–100
  • Total infrastructure: ~$100–150/month, plus Claude API usage

This is meaningfully more than the NAS-based setup (~$0/month plus electricity). The trade-off is professional reliability, automatic backups, real observability, and the ability to scale. For a system that's targeting "as close to hedge fund grade as possible" and trading real money, this is reasonable.

Five end-to-end scenarios

The architecture only matters if you can feel how it behaves. Here are five concrete scenarios — three normal-path, two failure-path. Each one walks through what happens, naming services and events.

Scenario 1 — normal path
A market arrives, gets evaluated, the bot places a real bet
  1. data-svc on its scheduled poll fetches active markets from Kalshi. For each market, it publishes market.tick.kalshi.KXFED-26JUN-50 with current price, volume, etc.
  2. strategy-timely subscribes to market.tick.kalshi.>. It receives the event, applies its filters (price band, spread, resolution date). Survives the filters.
  3. strategy-timely requests an edge analysis: publishes data.research.edge.request.KXFED-26JUN-50.
  4. data-svc subscribes to edge requests. Calls Anthropic Claude API with the market context. Receives back JSON with edge value, recommended side, confidence, reason. Publishes data.research.edge.KXFED-26JUN-50.
  5. strategy-timely receives the edge analysis. Combines it with the market data, decides to bet. Generates a correlation_id 7f3a2c. Publishes order.proposed.timely with payload: ticker, side, suggested amount, edge, confidence, strategy="TIMELY".
  6. risk-svc subscribes to order.proposed.>. Receives the proposal. Reads current bankroll from local cache (kept fresh by portfolio.updated events). Runs gate stack: status check, weekly loss limit, exposure cap, ticker concentration, contradictory positions. All pass. Computes Kelly size. Publishes order.approved.timely with sized amount, same correlation_id 7f3a2c.
  7. oms-svc subscribes to order.approved.>. Generates an internal order_id ord_abc123. Writes order_created event to its PostgreSQL log. Publishes order.submitted.ord_abc123 with full order details, correlation_id 7f3a2c.
  8. ems-svc (live mode) subscribes to order.submitted.>. Calls Kalshi create_order API. Kalshi responds with success and a venue order ID. Publishes order.acknowledged.ord_abc123.
  9. oms-svc hears the acknowledgment, writes order_acknowledged event, updates state.
  10. Moments later, Kalshi sends a fill notification (or ems-svc polls for fills, depending on Kalshi capabilities). ems-svc publishes order.filled.ord_abc123 with fill details.
  11. oms-svc records the fill event.
  12. pms-svc subscribes to order.filled.>. Records a bet_placed event in its portfolio log. Updates positions projection. Publishes portfolio.updated.
  13. telegram-svc subscribes to order.filled.>. Sends Filippo a Telegram message: "🎯 TIMELY placed: KXFED-26JUN-50 YES @ 22¢ for $5.00 (50 contracts)."

Total elapsed time: typically 2–5 seconds from market tick to filled bet. Twelve services touched. One correlation_id traces the entire flow. In Grafana Tempo you can see the whole journey as a single distributed trace.

Scenario 2 — normal path
A bet resolves, P&L flows through the system, bankroll updates

The Phase 2 bug ("bankroll only goes up") is structurally impossible in this flow.

  1. data-svc on its 30-minute resolution check polls Kalshi for markets where we hold positions. Detects KXFED-26JUN-50 has settled YES.
  2. data-svc publishes market.state.settled.KXFED-26JUN-50 with the final result.
  3. pms-svc subscribes to market.state.settled.>. Looks up its open position on this ticker. We hold 50 YES contracts.
  4. pms-svc computes outcome: market settled YES, we held YES, so we won. Payout = 50 × $1.00 = $50. Original cost was $5. Net gain is $45.
  5. pms-svc appends two events to its event log: position_closed (removes the position), then bet_won (delta_usd: +$50, attributed to TIMELY strategy and the Fed-rate category).
  6. pms-svc updates projections: positions projection no longer shows the ticker; bankroll projection increases by $50; P&L-by-strategy projection credits TIMELY with +$45 realized.
  7. pms-svc publishes portfolio.updated and pnl.realized.timely.fed_rate.
  8. risk-svc subscribes to portfolio.updated, refreshes its local cache of bankroll and exposures.
  9. reporting-svc records the resolution for the daily/weekly summary.
  10. telegram-svc sends Filippo a Telegram message: "✅ KXFED-26JUN-50 settled YES. TIMELY won +$45.00 on $5.00 stake (9.0x). New bankroll: $X."

For a losing bet the flow is identical, but the events are bet_lost with negative delta_usd. Bankroll decreases. The same single code path handles wins and losses — there's no separate "decrement" path that could be missing. There's just an event with a delta, and the delta might be positive or negative.

Scenario 3 — shadow / paper mode
Shadow runs in parallel, evaluates the same markets, never spends money

This replaces the old shadow_bot.py. There is no separate codebase. Same images, different namespace, different config.

  1. The trading-paper namespace is running. Same eight services as trading-prod. Same docker images. Different config: EMS_MODE=paper, separate database (pms_db_paper, oms_db_paper), starting bankroll seeded to a configurable amount (e.g. $1,000 virtual).
  2. Both namespaces independently fetch market data. Both run the same TIMELY strategy. Both get the same edge analysis from Claude (this is fine — paper and prod can hit the same Anthropic API).
  3. When TIMELY in paper proposes order.proposed.timely, the paper risk-svc evaluates it. The paper oms-svc submits it. The paper ems-svc (in paper mode) does not call Kalshi's create_order. Instead it simulates a fill at the current ask price.
  4. Paper ems-svc publishes order.filled.<order_id> with the simulated fill. Paper pms-svc records the bet against the paper bankroll.
  5. When the market resolves (this is real — the market really did resolve), paper data-svc publishes market.state.settled. Paper pms-svc records the win or loss against the simulated position. Paper bankroll moves.
  6. Each week, reporting-svc generates a comparison: live vs paper performance, side by side. Same strategies, different starting capital, different time of running. Allows direct measurement of strategy quality.

Crucially: the paper environment can run new strategies before they go live. Want to test a new strategy idea? Deploy it as strategy-newidea only in trading-paper. Watch its behavior for 2-3 weeks. Promote to prod only when paper data shows it works. The R&D content currently in shadow_bot.py (multi-model AI consensus, Manifold/Metaculus, news sentiment) gets either promoted into separate experimental services running in paper, or archived if it isn't carrying its weight. Section 09 has more detail.

Scenario 4 — adding a new strategy
You want to try a new strategy idea. How does it get into the system?
  1. Peter creates a new directory: services/strategy-momentum/. Copies the structure of an existing strategy service (each strategy is structurally identical — a NATS subscriber, a decision function, a NATS publisher).
  2. Peter writes the strategy logic: subscribe to market.tick.> and data.research.edge.>, decide if/when to propose, publish order.proposed.momentum.
  3. Peter writes unit tests against mock NATS messages. Integration tests against a local NATS + mock data-svc.
  4. Peter pushes the branch. CI runs. PR opens. Filippo reviews. Merge to main.
  5. GitHub Actions builds a new Docker image: strategy-momentum:abc123.
  6. Peter adds a Kubernetes manifest for the new service to the deployments repo. The manifest specifies: deploy to trading-paper namespace only (not prod yet).
  7. Argo CD applies the manifest. The new service starts in paper. Begins emitting heartbeats and (when conditions trigger) order.proposed.momentum.
  8. Existing risk-svc, oms-svc, ems-svc (paper), pms-svc require zero changes. They were already subscribing to order.proposed.>, which matches the new strategy's events.
  9. For 2-3 weeks the strategy runs in paper. Peter and Filippo watch the metrics, the simulated P&L, the win rate, the strategy's reasoning logs.
  10. If results are good: update the manifest to also deploy to trading-prod. Argo CD picks it up. Now it's running live.
  11. If results are bad: kill the paper deployment. The strategy never went live. Total damage: zero dollars.

Adding a new strategy in the old monolithic bot would require touching the scheduler, the gate stack, the bet recorder, the Telegram alerts, the reporting code. Six files. Shared state. New strategy = real risk of breaking existing strategies. In this architecture, a new strategy is one new directory and one new manifest. Zero changes to existing code. Existing strategies cannot be affected.

Scenario 5 — failure path
It's 2 AM. Telegram fires "Bot stopped placing bets." What do you do?

This is the 2-AM debugging story. The architecture's investment in observability pays off here.

  1. Telegram alert fires. The alert was triggered by alertmanager based on a Prometheus rule: "if no order.filled events from trading-prod in 60 minutes during expected market hours, page."
  2. You open Grafana on your phone. Go to the "trading-prod overview" dashboard. You see the metric: orders/minute dropped to zero at 01:43 UTC.
  3. You look at the per-service health metrics. data-svc is healthy. strategy services are emitting heartbeats. risk-svc is healthy. oms-svc is healthy. ems-svc has a "request_failed" rate at 100%.
  4. You click into ems-svc logs in Loki. You filter by level=ERROR. You see: "Kalshi API returned 503 since 01:43 UTC. Retried 47 times. Backing off."
  5. You confirm Kalshi is genuinely down by hitting their status page. It is.
  6. You check that the system is behaving correctly during the outage: are order.approved events piling up in NATS? You query the NATS dashboard. Yes — about 12 approved orders are waiting in the stream, will be replayed when ems-svc can reach Kalshi again.
  7. You check pms-svc for accuracy: bankroll is unchanged, no positions opened during outage. Correct.
  8. You decide: nothing to fix. Kalshi will come back. Orders will replay. Go back to bed.
  9. 4 AM. Kalshi recovers. ems-svc's circuit breaker opens. Replays the queued orders. Most still want to be placed (markets haven't moved much). A few have stale prices and are auto-cancelled by the OMS due to time-in-force expiration. Good behavior — we don't want to place orders based on 2-hour-old market data.
  10. Morning Telegram summary: "Kalshi outage 01:43-04:12 UTC. 8 orders queued + replayed successfully, 4 auto-cancelled (stale)."

In the old bot, a 2-AM Kalshi outage meant: bot crashes, no events recorded, when Kalshi comes back the bot is in an unknown state, manual intervention required. In this architecture: bot pauses gracefully, queued events resume on recovery, no manual intervention needed, the whole incident is in the event log for post-mortem. This is the difference between a hobby system and a production system.

Shadow bot — finally redefined as a paper environment

The audit found that shadow_bot.py had drifted into something incoherent. It was supposed to be a paper-trading mirror of the real bot. It became a research lab — multi-model AI consensus, Manifold/Metaculus integration, news sentiment, Google Trends, ten "risk extensions," dead Polymarket scanning. It mixed two completely different concerns into one process.

In the new architecture, those two concerns get cleanly separated.

Concern 1 — the paper environment

This is what shadow should have been. A complete mirror of the live system, running on the same code with simulated execution. Already designed: it's the trading-paper Kubernetes namespace from Section 07. Same images, different config, separate database. It exists for two purposes:

  • Validating strategy changes before they go live. Any strategy change deploys to paper first. Watch for 2-3 weeks. Promote to prod when confident.
  • Continuous comparison. Live and paper run the same logic. Differences in their results reveal whether live execution is slipping (bad fills, missed orders) versus the theoretical performance of the strategy.

Concern 2 — the research lab

The genuinely experimental ideas — multi-model AI consensus, alternative probability sources, sentiment integration — these are research, not paper trading. They belong in a separate space.

Two acceptable homes for them:

  • Experimental strategy services in paper. If the idea is "use multi-model consensus instead of single-model edge detection," that's a new strategy: strategy-consensus-experimental. Runs only in paper. Has its own metrics. After 2-3 weeks, you can compare its paper P&L against the standard strategy-timely running in the same paper environment. Apples-to-apples.
  • Offline research notebooks. Some of the audit's R&D items (Google Trends data, news sentiment correlations) are statistical research, not trading logic. They belong in Jupyter notebooks reading historical event logs from the PostgreSQL ledger. No need to run them as services.

What happens to the existing shadow_bot.py code

  • Multi-model AI consensus. Becomes strategy-consensus-experimental in paper. Compared against single-model TIMELY. Promoted only if it actually outperforms.
  • Manifold/Metaculus integration. Becomes a new adapter in data-svc: manifold_client.py, metaculus_client.py. They emit data.fundamental.manifold.<ticker> events. A future strategy can subscribe.
  • News sentiment / Google Trends. Becomes data.news.sentiment events from data-svc. Strategies that want them can subscribe. Strategies that don't, ignore them.
  • The 10 "risk extensions." Each is evaluated individually. Genuine risk improvements get folded into risk-svc. Speculative ones get archived in git history with a note explaining why they were considered and not adopted.
  • Polymarket scanning. If we want it, it becomes a real adapter in data-svc with its own strategy-arb behavior. If we don't, it gets deleted.
The principle: there is no place in the new architecture for "stuff we kind of want to try, mixed in with the live trading code." Everything is either (a) running in production, (b) running in paper as a clean experiment, or (c) in research notebooks. No more "shadow as a junk drawer."

MCP integration — the bot as a first-class AI-callable system

The Model Context Protocol (MCP) is Anthropic's standard for letting AI models discover and invoke tools. In the v1 architecture, MCP was a future consideration. In this architecture, MCP is a first-class service from day one. The bot doesn't just get used by AI — it is an AI-callable system.

Two directions of MCP

Direction A — the bot exposes itself as an MCP server

mcp-svc exposes a set of tools that any MCP client (Claude in chat, Claude Code, future agents) can call. These tools wrap the same underlying capabilities the rest of the system uses, just with an MCP transport layer.

Tools the MCP server exposes:

  • Read tools (no auth required for trusted clients):
  • get_state() — current bankroll, open positions, system status
  • get_recent_bets(since: datetime, limit: int) — bets placed in time window
  • get_strategy_performance(strategy: str, period: str) — win rate, P&L
  • get_event_stream(filter: dict, limit: int) — raw event log query for debugging
  • get_open_positions() — current positions with mark-to-market
  • get_pnl_breakdown(by: 'strategy' | 'category' | 'time') — P&L attribution
  • Read+simulate tools:
  • simulate_bet(ticker, side, amount) — what would the bot do? No actual placement.
  • Write tools (require explicit auth/confirmation):
  • trigger_reconciliation() — manually run venue reconciliation
  • pause_strategy(strategy: str) — stop a strategy from placing new orders
  • resume_strategy(strategy: str) — resume a paused strategy
  • pause_all() — emergency stop (all strategies, no new orders)

Each MCP tool is a thin wrapper. get_state() queries pms-svc's projections. pause_strategy() publishes a system.pause.requested event with the strategy name. The MCP server itself contains no business logic — it's a translation layer between MCP requests and NATS events / database queries.

Direction B — the bot consumes external MCP tools

data-svc can be configured to consume external MCP tools as data sources. Connect an MCP that provides news headlines? data-svc has an MCP client adapter. Connect an MCP that aggregates polling data? Same adapter, different config.

When external MCP tools are configured, data-svc emits their data through the same internal subjects as native data sources. data.news.<ticker> doesn't care whether the source was a direct API call or an MCP tool. Strategies subscribe and react identically.

What this gives Filippo and Peter

  • "What's the bot doing right now?" Open Claude, ask. Claude calls get_state(), summarizes. No SSH, no copy-paste.
  • "Why did TIMELY pass on KXFED yesterday?" Claude calls get_event_stream({strategy: 'timely', subject: 'strategy.skipped'}) and reads back the reason logged by the strategy.
  • "How would the bot bet on this hypothetical market?" Claude calls simulate_bet() with the parameters. Returns the proposed action without placing an order.
  • "Pause everything, market's about to do something weird." Filippo asks Claude to pause. Claude calls pause_all() after confirming with Filippo. Risk-svc receives the event, stops approving new orders.

Authentication and authorization

The MCP server has three permission tiers:

  • Read — no auth needed for trusted local sessions; basic API key for remote.
  • Simulate — same as read.
  • Write (pause, trigger, etc.) — explicit human confirmation required. The MCP server prompts the calling agent to surface a confirmation prompt to the human user before executing. (This is built into the MCP protocol via the elicitation capability.)

This means: even if a Claude session "decides" the bot should be paused, the action does not execute until Filippo or Peter clicks confirm in the chat UI. The bot cannot be controlled by an agent without human in the loop.

Why MCP is in the design from day one and not deferred: putting MCP in later means retrofitting authentication, retrofitting tool boundaries, retrofitting the mapping from internal events to external tool surface. Building it from day one means every service was designed knowing it might be queried via MCP. The marginal cost is small. The marginal benefit is large: from day one, the bot is something Claude can reason about as a first-class system, not an opaque process.

Migration roadmap — 7 phases, ~6 months realistic

This is a realistic timeline. Not optimistic. Two technical people (or one technical + one supportive) working consistent evenings and weekends. Each phase delivers measurable progress and a system that is functional at that phase. Each phase ends with the existing bot still running, on the NAS, until the new system is genuinely ready.

Phase 0 — keep the lights on

Duration: ongoing throughout migration. Effort: minimal.

The current bot stays paused (per the audit synthesis), or runs at a tiny scale that's safe. The migration doesn't require us to be actively trading during the build. If you do resume trading during migration, do it on the existing bot with the audit's bug fixes applied (notably the bankroll accounting fix), not on the half-built new system.

  • Provision DigitalOcean Kubernetes cluster (or chosen alternative)
  • Deploy NATS JetStream cluster (3 replicas, persistent storage)
  • Deploy LGTM observability stack (Prometheus, Grafana, Loki, Tempo)
  • Provision managed PostgreSQL, set up oms_db, pms_db, reporting_db

  • Set up GitHub Actions CI/CD pipeline + Argo CD
  • Set up sealed-secrets for credentials
  • Set up CloudFlare tunnel
  • Create trading-paper namespace; trading-prod exists but empty

Deliverable: a functional empty cluster with all infrastructure running. No trading services yet. You can kubectl apply a hello-world service and see it appear in Grafana with logs and metrics.

Phase 2 — core data layer (3-4 weeks)

  • Build oms-svc with the event-sourced order log
  • Build pms-svc with the event-sourced portfolio log
  • Build the shared bot-events Python package (event schemas, Pydantic models)
  • Deploy all three services to trading-paper namespace
  • Verify end-to-end: data-svc emits market.tick events, you can see them in Grafana
  • Verify event-sourcing: manually inject a deposit event, verify bankroll projection updates

Deliverable: the data backbone works. No strategies yet, no execution yet. But you have a system that ingests market data, has working event-sourced ledgers, and is fully observable.

Phase 3 — first strategy end-to-end (2-3 weeks)

  • Build ems-svc in paper mode only (simulated fills)
  • Run end-to-end: a market arrives, TIMELY proposes, risk approves, OMS records, EMS simulates a fill, PMS records the bet
  • Watch in Grafana Tempo: see the full distributed trace of one bet

Deliverable: the first strategy runs end-to-end in paper. This validates the entire architecture with a real workload before any real money is involved.

Phase 4 — go live with TIMELY only (2-3 weeks)

  • Build ems-svc in live mode (real Kalshi orders)
  • Build telegram-svc with basic alerting
  • Set up reconciliation jobs in OMS and PMS
  • Deploy all services to trading-prod namespace
  • Run with tiny bankroll ($50-100) for 2-3 weeks; compare results to paper running same strategy
  • Monitor reconciliation alerts daily; address any drift immediately

Deliverable: the new architecture is live, trading real money, with TIMELY only. The old bot can be retired. This is the milestone where "we have a new bot."

Phase 5 — port the remaining strategies (3-5 weeks)

  • strategy-midsel — the exit strategy
  • strategy-arb — cross-platform arb (requires Polymarket adapter in data-svc first)
  • Add reporting-svc with daily/weekly reports
  • Add the prompt-fragment strategies (FADHYPE, NICHDOM) to the AI edge detector
  • Each strategy goes paper → prod through the standard flow

Deliverable: all of the existing bot's actual functionality is now in the new architecture, plus better observability, plus better reliability.

Phase 6 — hardening and MCP (3-4 weeks)

  • Build mcp-svc with the read tools
  • Add the simulate tools to MCP
  • Add the write tools (pause, resume) with auth
  • Stress-test failure scenarios: kill ems-svc during a fill, kill the database, kill NATS
  • Verify the system recovers correctly in each case
  • Write runbooks for each known failure mode
  • Set up alerting rules in Prometheus alertmanager

Deliverable: the system is genuinely production-grade. MCP exposes the bot to Claude as a first-class system. Operational practices (runbooks, alerts) are in place.

Phase 7 — research and growth (ongoing)

  • Move shadow R&D content into experimental strategy services in paper
  • Begin Bayesian-Kelly sizing experiment (paper first, then prod if it outperforms)
  • Add new data sources as MCPs or as direct adapters
  • Add new strategies as new services
  • This phase has no end date — it's how the bot grows

Total realistic timeline

Phases 1–6: about 16-23 weeks of mostly evenings/weekends. Call it 5-6 months of calendar time. If Peter and Filippo can dedicate full days, it compresses to 2-3 months. The point is: this isn't a weekend project, and pretending it is would lead to an under-built system. Setting the right expectation upfront is part of doing this professionally.

The risk to manage during migration: the temptation to fix bugs while porting. Resist it. Migration goal: same behavior, new architecture. Behavioral changes (new strategies, Bayesian-Kelly, modified thresholds) come after migration is done, in separate PRs that can be isolated and rolled back. Conflating "rebuild" with "improve" is how rewrites fail. The audit identified specific bugs (Phase 2 bankroll accounting being the worst); the architecture fixes those specific bugs structurally. That's not "improvement during migration" — that's "the architecture is better." But things like new strategies, new sizing methods, new prompt structures: all of that comes later.

Risks, failure modes, and what could derail this build

Honest assessment of what could go wrong with this plan. Not "could the bot lose money" — the audit synthesis covers that. Specifically: what could prevent us from successfully building the new system as designed.

Build risks

  • Scope creep during migration. The biggest risk. The temptation to add new strategies, new data sources, or new sizing logic while porting is strong. Mitigation: strict rule that migration phases produce same behavior, new architecture; improvements come in separate phases after.
  • Underestimating the time. 5-6 months is realistic for evenings/weekends. People consistently underestimate distributed systems work. Mitigation: progress measured by phase completion, not hours; willingness to extend timeline rather than ship a half-built system to prod.
  • Operational learning curve. Kubernetes, NATS, Argo CD, observability stack are all new tools to learn well. First few weeks will feel slow. Mitigation: budget Phase 1 explicitly as "infrastructure foundation," accept that it produces no trading capability but lots of learning.
  • Over-engineering individual services. Each service is small (~500-2000 lines of Python). Don't gold-plate them. Mitigation: code review with the question "is this complexity earning its keep?"

Run-time risks unique to this architecture

  • NATS becomes a single point of failure. If NATS is down, no service can communicate. Mitigation: 3-replica JetStream cluster; NATS is among the most operationally simple distributed systems; regular backup of stream contents.
  • Database becomes a single point of failure. If PostgreSQL is unreachable, OMS and PMS can't write. Mitigation: managed Postgres with 99.9% SLA; daily backups; OMS and PMS gracefully degrade (refuse new orders, don't lose existing state).
  • Event schema evolution breaks consumers. Adding a required field to an event without versioning will break every consumer of that event. Mitigation: strict schema rules from Section 05; all events versioned; CI checks for backward-incompatible schema changes.
  • Eventual consistency confusion. Because services communicate via events, the system has eventual consistency. Strategy proposes order at time T; risk evaluates at T+50ms with portfolio state from T-200ms. Mitigation: design strategies to be tolerant of slightly stale state; risk-svc rechecks bankroll at decision time.
  • Distributed system debugging is harder than monolithic debugging. A bug spanning 3 services is harder to reason about than a bug in one process. Mitigation: distributed tracing in Tempo with correlation_ids; structured logging in Loki; comprehensive integration tests.

Cost risks

  • Anthropic API costs. Calling Claude on every market evaluation can add up. With 14 daily TIMELY scans × 50 markets × multiple models = potentially $5-20/day. Mitigation: caching of edge analyses (within reasonable freshness windows); tiered model selection (cheap model for first-pass filtering, expensive model for shortlist); budget alerting in data-svc.
  • Cluster costs creep. Adding more strategies adds more pods. More pods need more nodes. Mitigation: Kubernetes Vertical Pod Autoscaler; monthly cost review; cap on total cluster size with manual approval to expand.
  • Data egress fees. Cloud providers charge for outbound traffic. Polling Kalshi heavily could cost $5-10/month in egress. Mitigation: monitor; cache market data; aggregate API calls.

What would tell us this design is wrong?

Worth committing to ahead of time: signs that would force a redesign rather than an iteration.

  • Phase 1 takes >6 weeks. → infrastructure complexity is too high; consider Hetzner + K3s or even a beefier NAS-based deployment.
  • By Phase 4, end-to-end latency is >1 second. → service architecture has too many hops; consider collapsing risk + OMS into one service, or strategy + risk.
  • Cluster costs exceed $300/month with a single bankroll trading. → over-provisioned; reduce node count or move some services to serverless functions.
  • By Phase 5, deploying a new strategy still requires changes to multiple services. → boundaries are wrong; refactor before going further.
  • After 3 months in production (Phase 6+), more time is spent on infrastructure than on improving the trading logic. → architecture is too heavy for the team; simplify.

None of these are prohibitions. They're checkpoints. If we hit one, it's a signal to step back and reconsider, not necessarily abandon.

Glossary

TermPlain English
MicroservicesAn architectural pattern where the system is broken into small, independently-deployable services that communicate over a network.
OMS (Order Management System)The hedge fund component that tracks the lifecycle of every order — created, submitted, filled, cancelled. The system of record for orders.
EMS (Execution Management System)The component that actually talks to venues to place orders. Separated from the OMS because venue connectivity is messy and venue-specific.
PMS (Portfolio Management System)The component that tracks current positions, P&L, and bankroll. Answers "what do we own and what is it worth?"
Risk EngineThe component that decides whether a proposed order is allowed to fly, applies sizing logic, enforces limits.
SleeveHedge fund term for an independent strategy. Used in this document interchangeably with "strategy service."
Event-driven architectureSystem design where components communicate by emitting and consuming events rather than calling each other directly.
Event sourcingStoring every change to state as an immutable event in a log. Current state is computed by replaying events. Like an accounting ledger.
ProjectionA read model derived from the event log. Bankroll is a projection. Open positions are a projection. Can be rebuilt from events at any time.
Message busThe infrastructure that carries events between services. We use NATS JetStream.
NATS JetStreamA modern message bus, simpler than Kafka but with persistence and replay. Open source, single Go binary, designed for microservices.
Subject (NATS)NATS's term for a topic. Hierarchical, dot-separated. order.proposed.timely matches the wildcard order.proposed.>.
Correlation IDA unique ID attached to every event in a chain. Lets you trace one bet from idea to fill across all services.
IdempotencyProperty of a function such that calling it twice has the same effect as calling it once. Required for at-least-once delivery systems.
At-least-once deliveryMessage bus guarantee that every message will be delivered, but might be delivered more than once. Consumers must be idempotent.
Kubernetes / k8sOpen-source platform for running containers in production. Handles deployments, scaling, networking, restarts.
Pod (k8s)A running container (or small group of related containers) — the smallest deployable unit in Kubernetes.
Namespace (k8s)A logical isolation boundary within a cluster. We use trading-prod and trading-paper as separate namespaces.
DOKSDigitalOcean Kubernetes Service. Managed Kubernetes — they run the control plane, you run the workloads.
Argo CDA GitOps deployment tool. It watches a git repo of Kubernetes manifests and applies changes to the cluster.
LGTM stackLoki + Grafana + Tempo + Mimir. The standard open-source observability stack from Grafana Labs.
LokiLog aggregation. Like Elasticsearch but cheaper. Indexes labels, not log content.
TempoDistributed tracing backend. Stores spans from OpenTelemetry. Lets you see end-to-end traces.
PrometheusMetrics database. Scrapes /metrics endpoints from services. Standard in Kubernetes.
GrafanaVisualization tool. Sits on top of Prometheus, Loki, and Tempo. Where you build dashboards and explore data.
OpenTelemetryVendor-neutral standard for emitting metrics, logs, and traces. Each service uses the OTel SDK.
Sealed-secretsA way to commit encrypted secrets to git, decrypted only by the cluster. Lighter alternative to Vault.
Dry-run / paper modeSame code path as live, but execution is simulated instead of placing real orders. Inspired by Freqtrade's --dry-run.

MCP (Model Context Protocol)Anthropic's standard for AI assistants to discover and call external tools. Lets Claude (in chat) directly query and command the bot.
