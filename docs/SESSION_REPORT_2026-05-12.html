01

Where we started

The session opened on Filippo's MacBook with Phase 1 at 11/12 from session 5. Task 12 (the runbook) was the only ticket left in the original Phase 1 scope, but we had no real verification that Task 10 (LGTM observability) was actually functional beyond "Prometheus and Tempo are up." The first move was to write the runbook and close Phase 1; the second move was to verify what we'd shipped. The verification revealed three Phase 1.5 problems — invisible until tested, none of them visible from Argo CD's "Synced/Healthy" status:

  • Grafana had only 2 of 4 expected datasources (Prometheus + Alertmanager — no Loki, no Tempo)
  • Loki was running but had no log shipper, so it had only loki-canary self-test data
  • No app-of-apps reconciling deploy/applications/, so every YAML change to date had been manually kubectl apply'd — git and cluster were drifting silently

The team chose to fix all three plus tackle Phase 2's event vocabulary before stopping. DOKS apiserver was unstable throughout the night — at least four EOF incidents on kubectl writes, one ~25-minute sustained outage, kube-state-metrics restart count climbed from 28 → 47 over the session. We worked around DOKS twice (direct ConfigMap patch for datasources; abandoned Argo retry for kube-prometheus-stack sync).

Task 4 — Phase 1.5 Problem 2: Grafana Alloy log shipper deployed (three iterations)

Deploying the log shipper took three commits because the first design had a fatal interaction with single-binary Loki under load. Each iteration was a clean test of the GitOps pipeline we'd just shipped.

  • v1 — commit 8e192c7 — Alloy DaemonSet, K8s-API-based loki.source.kubernetes. First end-to-end test of app-of-apps: pushed to git, Argo detected and deployed automatically (~3min29s from push to Synced). BUT Alloy started backfilling 3+ days of pod logs from epoch on first discovery and crushed single-binary Loki — readiness probes failed 26 times in 6.5 min, Loki dropped from service endpoints, Alloy got connection refused.
  • v2 — commit 7216a72 — Switched to file-based collection. Web search confirmed tail_from_end is not supported on loki.source.kubernetes (grafana/alloy#3550, open since May 2025). Stopped the bleed first by scaling DaemonSet to 0 via nodeSelector: midas/disabled=true (Loki recovered in <30s). Rewrote with local.file_match reading /var/log/pods/*$UID/*.log via alloy.mounts.varlog: true, plus loki.source.file with tail_from_end = true. hello-svc namespace label registered in Loki, but cluster-wide steady-state ingest still saturated query path.
  • v3 — commit 6d25248 — Added drop relabel rule for kube-system|monitoring namespaces (DOKS-managed chatter + observability self-logs). Reconciled via GitOps in 11 seconds. Verified with count_over_time instant queries (the limit-cap diagnostic trap was caught by Filippo): kube-system 0 lines/2min, monitoring 0 lines/2min, hello-svc 16 lines/2min (matches the 10-second health-probe rate), argocd 130 lines/2min, Loki /ready stable.
Why it matters: Closes the largest gap in v2 §08. Logs now flow from every pod to Loki with proper namespace/pod/container/app/node labels, queryable from Grafana. Phase 2 services (data-svc, oms-svc, pms-svc) will be observable from the moment they deploy — no per-service log shipper setup, no tribal knowledge. The three-iteration arc also stress-tested v2 §09 (GitOps): we pushed three live config changes and Argo applied them all without manual intervention. The pattern is real.

Each event = one commit. Each follows the established BaseEvent pattern (Pydantic v2, frozen=True, extra="forbid", ClassVar event_type/event_version with __init_subclass__ enforcement, wrap serializer for class constants).

Suite went 16 → 120 passing tests over these seven commits.

Why it matters: This is v2 §04 (bot-events package) in full. Every Phase 2 service (data-svc, oms-svc, pms-svc) imports these types — they cannot be built without them. Designing the schema first, with tests, means we will never have a "what was the field name again?" moment during service implementation. Key event-sourcing discipline encoded throughout: order-level facts (side, direction, limit_price) live on OrderPlacedEvent only and are joined via exchange_order_id to OrderFilled/OrderCancelled events; bankroll uses an event-sourced delta+checksum pattern with no mutable balance field (binding constraint #1); realized P&L is pre-computed on PositionClosedEvent in dollars (signed for losses), with pms-svc as the canonical source so other services don't replay fill chains. Decimal-in-cents for prices, Decimal-in-dollars for money. No floats anywhere.

Decisions made inline

DecisionChoiceWhy
app-of-apps scopeSingle Application, flat directory, manages itself recursivelySimpler than nested folders; one bootstrap; no migration churn moving existing 7 YAMLs
Log shipper: API vs fileFile-based (loki.source.file + local.file_match)K8s-API approach doesn't support tail_from_end (grafana/alloy#3550). File-based reads /var/log/pods/* with tail_from_end = true; standard production pattern
Log shipper: scopeDrop kube-system + monitoring namespaces at relabel stageDOKS-managed chatter + observability self-logs would saturate single-binary Loki. Filter at source, not in Loki, so the bytes never travel
Datasource fix deliveryDirect ConfigMap patch (bypassing stuck Argo sync)Apiserver was EOF'ing mid-Argo-sync. Bypassing the chart's entire sync to apply ONE ConfigMap change reduced blast radius to zero
Order-level facts duplicationNOT duplicated across order eventsEvent-sourcing discipline. Side/direction/limit_price live on OrderPlacedEvent; consumers join via exchange_order_id. Trade-off: more joins, but events cannot internally contradict each other
Realized P&LPre-computed on PositionClosedEvent in dollars, signedReporting/risk/learning consumers shouldn't each replay the fill chain. pms-svc is canonical. The event becomes the receipt.
Bankroll modelEvent-sourced delta + checksum (new_balance is a checksum, not a source of truth)Binding constraint #1 ("bankroll only goes up" was the old bug). Current bankroll = sum of all BankrollChangedEvent deltas. new_balance is what the sum should be — if it doesn't match, there's a bug.
PositionUpdatedEventNot modeled in v1Position growth derivable from replaying fill chain. Adding the event type is non-trivial complexity for marginal win. Revisit if downstream consumers actually need explicit signals.
kps stuck syncAbandoned tonight; functional fix already liveTwo cancel-and-retry attempts both failed (second sync trigger swallowed). Evidence captured for DO ticket. The OutOfSync state has no functional impact.
