Why this session matters

Tonight redesigned data-svc's market selection from a 20-market firehose (publishing nothing useful) into a proper two-loop architecture matching production-grade prediction-market bots — slow discovery scan paginating the full universe, fast tick poll over the selected set. This is the data layer the rest of the v2 architecture sits on (v2 §04, §05): without a sane selected universe, every downstream service is reading noise. The architecture shipped clean. The cluster deploy then surfaced exactly the kind of real-data calibration gap our instrumentation was designed to make visible — fail-loud doing its job.

Task 3 — Design the two-loop market selection architecture

Researched production-grade prediction-market bots (ImMike's 10k-market Polymarket/Kalshi scanner, LayerX's Bregman bot, Trevor Lasn's arb writeups). Locked four design pivots away from earlier draft:

  1. Two loops, not one. Slow discovery (paginates all open markets, default 60s) maintains the selected universe. Fast tick poll (5s) consults the universe, fetches books only for selected tickers. Match loop cadence to data's actual change rate.
  2. Open scope, no allowlist. The pros let data flow broadly and put trade decisions at the strategy layer. Filippo's intent is explicitly "open to sports if they have opportunity" — a narrow allowlist would blind the system to exactly those opportunities.
  3. Tiered liquidity, two tiers to start. Named macro series (KXFED, KXPRES, KXECON, KXCPI, KXINX, KXHOUSERACE) get tight thresholds (2¢ spread, 50 volume). Everything else including sports gets default permissive (5¢ spread, 1000 volume).
  4. Re-evaluate at tick time. A market that goes thin between discovery cycles skips at publish — never published as junk. The (no_book/spread/volume) counts in poll logs become a live instrument.
Why it matters: implements v2 §04 (data-svc as the system's senses) and §05 (event bus contract). The two-loop split is what makes this scalable to thousands of markets without hammering Kalshi or NATS.

Fail-loud doing its job.

Rolled back via kubectl rollout undo — which stopped the crash-loop but did not revert the image, because the deployment pins by mutable :main tag with imagePullPolicy: Always. So we're now running the new flaky code on the cluster (one stable pod, restarting roughly once per heavy discovery cycle), publishing 0–1 markets, no consumers downstream, no harm.

Why it matters: first time our test-mocked architecture met real production Kalshi. Three concrete gaps now visible that no amount of mocked testing would have surfaced. The instrumentation we built specifically to expose this kind of failure (await-first, enriched logs, max_pages warning) all worked — we know exactly what went wrong because the system told us.

How this fits the v2 architecture (plain English)

The kitchen analogy: data-svc is the prep cook receiving deliveries from the wholesaler (Kalshi). Before tonight, the prep cook would walk to the door, accept the first 20 boxes from whoever was at the truck, ignore the rest, and report back "0 useful ingredients today." Tonight we rebuilt the prep station into two roles working together:

  • Slow walk-through (discovery_loop): Once a minute, the prep cook walks the whole loading dock, inventories every box, applies a quality test ("is this fresh enough? is the price reasonable?"), and keeps a list of which boxes are worth opening.
  • Fast pickup (tick_poll_loop): Every 5 seconds, the prep cook goes only to the boxes on the list, checks them again (since freshness can change), and announces the fresh ones to the rest of the kitchen.

04

Decisions made inline

  • Open scope over allowlist — pros do it, matches "open to sports if liquid" intent.
  • Two tiers (named-series tight, default permissive) — start simple, tune from logs. Premature tiering is the magic-number trap (Lesson 9).
  • Decimal not int for spreads — Kalshi prices are dollar-strings with 4 decimal places; real spreads can be 1.7¢.
  • Default volume floor = 1000 — cost governor for the fast loop. The most likely number to tune from real logs.
  • Await-first startup default — fail-loud at boot. Escape hatch DATA_SVC_DISCOVERY_AWAIT_AT_STARTUP=false for ops debugging.
  • Two-commit split for bisectability — pure logic separate from runtime wiring. If integration has a subtle bug, the pure layer underneath is still verified and good.
  • seeded= keyword on discovery_loop — eliminates the double-scan at startup. Self-documenting, no apologetic comment.
  • Push Commit A as temporary branch for independent CI verification — 90 seconds of work for permanent bisectability guarantee.
05

Issues + resolutions

Cluster deploy crash-loop

New pod kept getting killed by liveness probe (~70s) before startup discovery scan could finish (~103s). Root cause: no startupProbe in the deployment manifest. Resolution: rolled back to stop the hammering, accepted current state (pod stable-by-luck for the moment), carry the proper fix to next session.

Rollback that wasn't

kubectl rollout undo reverted the pod-template revision but the deployment pins the image by mutable :main tag with imagePullPolicy: Always — so the "old" ReplicaSet re-pulled :main which now resolves to the new image. Real rollback requires a GitOps change (pin by digest in Argo's source). Documented; deferred.

Selected=0 on discovery_loop scans

Every paginated cursor in the logs was sports/multi-game tickers (KXMVE*, KXMLBTOTAL*). No KXFED/KXPRES/KXECON appeared in the scanned 20,000 markets. Kalshi's default ordering front-loads tens of thousands of illiquid sports sub-markets, so our max_pages=20 cap truncates away the liquid markets we most want. Not a code bug — a real ordering/scope-strategy gap surfaced by the data.

In this project, conservative-instinct ("don't speculatively complicate") needs to lean toward FIX-IT, not LEAVE-IT, because the entire rebuild exists to unwind that cost. Two examples this session: double-discovery-scan and Commit A's CI verification. Both worth fixing; both fixed.
