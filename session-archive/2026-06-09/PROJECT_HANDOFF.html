What this doc is

Midas is a from-scratch rebuild of the Kalshi prediction-market trading bot. The legacy bot was audited and found structurally broken (bankroll only goes up, dead reconciliation, 8 strategies of which 2 dead, magic numbers, no schema, no tests). Midas is the deliberate replacement — multi-service, event-driven, tested first, designed against the v2 architecture document.

The three-doc orientation triangle:

  • This file (PROJECT_HANDOFF.html) — current state, always overwritten each session.
  • JOURNEY.md — the narrative arc connecting all 8 phases. Why each phase exists, why ordering matters.
  • Bot_Architecture_v2_Professional_Grade_April26_2026.html — the master 14-section architecture plan. Always defer to this for big-picture decisions.

What Midas is

Multi-service event-driven prediction-market trading system. Built around hedge-fund-style OMS/EMS/Risk separation. Currently in Phase 1 (cluster-up, data ingestion). Total realistic timeline ~5-6 months calendar across 8 phases. Repo: github.com/bakerlunch-ai/midas (private).

Where we are in the v2 architecture (orientation)

Kitchen analogy: the bot is a restaurant. data-svc is the prep cook receiving deliveries (Kalshi). strategy-svc is the head chef deciding what to cook (which trades to take). oms-svc is the line cook executing orders. pms-svc is the inventory clerk tracking what's in the pantry (open positions). risk-svc is the floor manager calling halts. Each station independent, communicating via the message bus (NATS).

What to do next

Open the next session here. The 5 things in priority order:

  1. Add startupProbe to data-svc deployment — fixes the liveness collision at startup. GitOps manifest change. initialDelaySeconds: 0, periodSeconds: 10, failureThreshold: 30 (5min grace).
  2. Pin data-svc image by digest in deploy manifests — required for real rollbacks. Otherwise kubectl rollout undo is cosmetic.
  3. Raise max_pages or paginate more selectively — Kalshi's 20k+ open markets are front-loaded with illiquid sports parlays, so our 20-page cap never reaches the liquid named-series we want.
  4. Tune liquidity thresholds from real data — env-var change. The default tier's 1000-volume floor is the most likely suspect.
  5. Investigate startup-seed vs loop-rescan selected-count discrepancy — startup got 4, re-scans got 0.
07

Decisions on record (locked)

  • Open scope, no allowlist (session 10). Ingest broadly, filter at strategy layer. Filippo: "open to sports if they have opportunity."
  • Two liquidity tiers (session 10). Named macro series tight; everything else (incl. sports) permissive. Tunable.
  • Re-evaluate at tick time, not just discovery (session 10). A market that goes thin between scans must skip at publish, not be published as junk.
  • Await-first startup is default (session 10). Fail loud at boot if discovery raises. Escape hatch DATA_SVC_DISCOVERY_AWAIT_AT_STARTUP=false.
  • seeded= keyword on discovery_loop (session 10). When True, loop sleeps before its first scan (avoids double-scan at boot).
  • Bisectable two-commit ships (session 10). Pure logic separate from runtime wiring. Each commit independently CI-verified.
  • Liquidity is a signal, not a gate (session 9). Measured per-market, attached to events. Strategies decide.
  • Position-safety seam (session 9 design, pending). Fast-poll set = selection-rules ∪ open-positions, always.

10

Working agreements

  1. Fix-it bias. When the fix is small and the gap is named, fix it. The legacy bot's structural failure was cumulative "leave it for now." Conservative-instinct needs to lean toward FIX-IT, not LEAVE-IT.
  2. "A green Build is not a green CI" — and a green rollback message is not a real rollback. Verify behavior, not just exit codes.
  3. Independent CI per commit. If a commit lands in a push-pair and we want bisectability, push it as its own branch tip first.
  4. Test-first. Failing tests against captured real-data shapes, then implement. Zero AssertionError baseline.
  5. Decisions inline. Filippo prefers fast forward motion. Flag significant decisions/risks before they execute, no planning docs unprompted.
  6. Plain English. Analogies preferred. Kitchen analogy is locked.
  7. Filippo says when to stop. Never asked.
11

The 10 binding constraints

  1. Bankroll only goes up — use event sourcing, not mutable balance fields
  2. Reconciliation never ran — must be on a scheduler
  3. Strategies as strings — use ClassVar + __init_subclass__ enforcement
  4. Eight strategies, two of which were dead code — delete what isn't deployed
  5. Risk gates duplicated in eight places — one canonical implementation only
  6. Shadow drifted into research lab — paper environment ≠ research
  7. State file 34 keys deep with no schema — Pydantic + JSON Schema, versioned
  8. The learning system never learned — every event has a reader
  9. Magic numbers everywhere — config in YAML/env, not code
  10. The bot grew faster than its tests — tests not optional, CI gates

Glossary

  • SelectedUniverse — in-memory frozenset of tickers data-svc considers worth polling. Updated by discovery_loop, consulted by tick_poll_loop.
  • Tight tier — named macro series (KXFED, KXPRES, KXECON, KXCPI, KXINX, KXHOUSERACE). 2¢ spread cap, 50 min volume.
  • Default tier — everything else including sports. 5¢ spread cap, 1000 min volume.
  • seeded=True — keyword on discovery_loop: caller already populated the universe (await-first startup), loop should sleep before its first scan to avoid duplicate.
  • JOURNEY.md — narrative arc connecting all 8 phases. Updated when phase progress shifts.
  • v2 architecture — Bot_Architecture_v2_Professional_Grade_April26_2026.html. 14 sections, 8-phase roadmap. The big-picture authority.
  • Switch-and-restore — pattern for pushing to bakerlunch-ai repo while keeping Pippo-min as the day-to-day active gh account.
  • Kitchen analogy — data-svc = prep cook; strategy-svc = head chef; oms-svc = line cook; pms-svc = inventory clerk; risk-svc = floor manager; NATS = intercom.
