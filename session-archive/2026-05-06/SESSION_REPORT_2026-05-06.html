How this fits the v2 architecture (plain English)

Every task this session moved one specific piece of the Bot Architecture v2 document from "designed on paper" to "running in the cluster." Here's the translation, in plain English, with the architecture v2 section reference for each piece.

The big picture, before this session

Imagine the bot v2 architecture as a professional kitchen with eight stations (the eight services in v2 §04 — data, oms, pms, strategy, risk, reporting, scheduler, mcp-gateway). For these stations to work, they need:

  • A building with electricity and plumbing (the Kubernetes cluster — done in earlier sessions, v2 §07)
  • A locked supply room where ingredients (database passwords, API keys) live encrypted (sealed-secrets — Task 7, v2 §07)
  • A communication system so each station can shout "order up!" to the next without phoning each other directly (NATS JetStream — Task 9, v2 §05)
  • Cameras and microphones in every station so the head chef can see what's happening (Loki + Tempo + Prometheus — Task 10, v2 §07)
  • A head chef who actually knows how to cook (the eight services themselves — Phase 2 onward, v2 §04)

This session built three of those four foundation pieces. The kitchen still has zero chefs. But the building is wired.

What each task corresponds to in v2

What we did v2 architecture reference What it unlocks
Task 7 — sealed-secrets controller installed and round-trip verified v2 §07 — "Operational stack → Secrets management." The architecture explicitly recommends sealed-secrets over Vault or cloud secret managers because it lets us commit encrypted credentials to git, which fits the GitOps model. Every Phase 2+ service can now read database/API credentials from Kubernetes Secrets. No more hardcoding, no more env-var copy-paste.
Task 8 — 4 real credentials sealed (3 Postgres users + Redis) v2 §06 — "Data layer → PostgreSQL with logical separation by service." Each service (oms-svc, pms-svc, reporting-svc) gets its own database user with access only to its own logical DB. Phase 2 services can connect to their respective databases on day one. Schema migrations and table creation happen inside each service's namespace; no cross-contamination.
Task 9 — NATS JetStream cluster with durability proven v2 §05 — "The message bus." This is the backbone of the event-sourced architecture. Every action in the system is an event published to NATS. Every state-change is reconstructable from the event log. Services can be added, removed, or replayed without coordination. This is what makes binding constraint #1 ("bankroll only goes up — use event sourcing") possible. Without JetStream, there's no event sourcing, and we'd be repeating the legacy bot's mutable-state mistake.
Task 10 (Loki + Tempo done) — log aggregation + distributed tracing running v2 §07 — "Observability stack." Loki = "what did the bot say?" Tempo = "when service A called service B which called service C, where did time get spent and where did it fail?" When Phase 2 services start emitting events, every event will be searchable as a log line and every cross-service interaction will be traceable. We'll know why a strategy fired, not just that it fired.
Task 10 (kps stuck) — Prometheus / Grafana / Alertmanager not running yet v2 §07 — "Metrics + alerting." The "what is each service doing right now" dashboards. Once fixed, we get cluster-wide CPU/RAM/network metrics, custom strategy-level metrics (win-rate, edge, P&L), and alert rules ("if daily loss exceeds X, page someone"). Until then: Loki + Tempo cover most of what we need to debug Phase 2 services. kps is "nice to have" not "must have" for Phase 2 to start.

Why this matters for the migration timeline

v2 §11 lays out an 8-phase migration roadmap. We're in Phase 1 (Infrastructure foundation). Phase 1 has 12 tasks. After this session: 9.5 of 12 done. The remaining 2.5 tasks are:

  • Task 10 finish — fix kube-prometheus-stack (or formally defer it; v2 says metrics are part of operational stack but not a blocker for service deployment)
  • Task 11 — hello-svc proof-of-life. This is the integration test that proves Phase 1 is actually done. A tiny service that connects to all four sealed credentials, talks to NATS, gets logs into Loki, traces into Tempo. If hello-svc works, every Phase 2 service can.
  • Task 12 — write the runbook (v2 §07 mentions ops documentation is part of the stack, not optional)

Translation: after one more session of similar quality, Phase 1 closes and Phase 2 begins. Phase 2 = the first three real services (data-svc, oms-svc, pms-svc, v2 §04). That's where Midas starts looking like a bot instead of looking like infrastructure.

What this session did NOT touch

To be honest about what's still abstract: tonight we built none of the eight services from v2 §04. We wrote no Python service code. No strategy logic. No risk gates. No order management. The bot still has zero ability to look at a market, decide anything, or place an order. Every Phase 2+ task is still ahead of us.

That's intentional and correct. v2 is explicit (§02, §11) that infrastructure-first is the right sequence — the legacy bot's biggest sin was building services on top of infrastructure that wasn't ready, which is what produced the bankroll-only-goes-up bug, the dead reconciliation, and the magic numbers everywhere. We're refusing to repeat that.

One-line summary: tonight we built the secret-storage system, the message bus, and half the observability stack — three of the four pillars from v2 §07 that every future service depends on. The kitchen is now wired for the chefs we'll hire in Phase 2.

08

Working agreement updates

Three new rules added based on this session's pain.

1. Credential sealing canonical pattern

For every database credential going into a SealedSecret, use this exact flow:

# Postgres users (oms_user / pms_user / reporting_user): doctl databases user get <cluster-uuid> <username> --format Password --no-header > /tmp/<name>-pw.txt HOST=$(doctl databases connection <cluster-uuid> --private --format Host --no-header) PORT=$(doctl databases connection <cluster-uuid> --private --format Port --no-header) PASSWORD=$(cat /tmp/<name>-pw.txt | tr -d '\n') echo -n "postgresql://<username>:${PASSWORD}@${HOST}:${PORT}/<db>?sslmode=require" > /tmp/<name>-conn.txt unset HOST PORT PASSWORD # Redis (Valkey) — user get returns 404, use connection URI instead: doctl databases connection <cluster-uuid> --private --format URI --no-header | tr -d '\n' > /tmp/redis-conn.txt

Never use the DigitalOcean web UI copy buttons. Never assemble connection strings manually in nano.

2. Verify before next sealing

After every kubeseal, apply the resulting file to the cluster, decode the resulting Secret, and confirm structure (single line, @ visible between password and host) before moving to the next credential. Sealing without verification is what produced the broken May-4 OMS file that didn't get caught until tonight.

3. 3-hour cap on credential-handling sessions

Tonight's three credential mishaps (key leak, host fragment, broken Redis sealing) all happened past the 3-hour mark. Stopping earlier next time. If credential work hasn't finished by hour 3, save state and resume next session.

Bonus rule: For diagnostic regexes that redact passwords, exclude @ from the character class so the URL structure remains visible. Pattern: [A-Za-z0-9!#$%^&*()_+=-]\{6,\}.
