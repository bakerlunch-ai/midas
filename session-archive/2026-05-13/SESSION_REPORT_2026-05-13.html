Task 4 — data-svc piece #2: FastAPI main.py with lifespan-managed KalshiClient (commit 07aa840)

Wrote services/data-svc/src/data_svc/main.py mirroring hello-svc's shape — an @asynccontextmanager lifespan that constructs httpx.AsyncClient, then KalshiClient with the http client injected, then runs a one-shot list_markets(limit=1) startup probe so bad Kalshi credentials crash-loop the pod instead of running silently. GET /health returns a dumb {"ok": true} liveness signal. Three tests added via httpx.MockTransport — no real Kalshi calls.

Why it matters: First step of v2 §05 (data-svc): the service has an entrypoint, a lifecycle, and a fail-loud probe. The pattern — @asynccontextmanager owns connection lifecycle, resources closure-captured (no app.state), dumb /health — becomes the canonical shape every Phase 2 service mirrors. oms-svc, pms-svc, and risk-svc will all look like this. Encoding the shape once means we won't relitigate it three more times.

Task 5 — Makefile fix: make test survives uv's UF_HIDDEN bug (commit e825e9e)

Discovered during Task 4 that uv run pytest on macOS Darwin 25 silently fails with ModuleNotFoundError: No module named 'bot_events' because uv sync sets the UF_HIDDEN flag on editable-install .pth files, and Python's site.py skips hidden .pth files silently. Worse, uv run re-hides them on every invocation, so re-running uv sync is a no-op fix. The Makefile's test target was rewritten to depend on a new _unhide-pth helper (chflags nohidden ..., no-op on Linux via || true) and to invoke .venv/bin/pytest directly, bypassing uv run's re-hide. install target also runs _unhide-pth after uv sync. Documented in RUNBOOK so future maintainers don't "simplify" it away.

Why it matters: v2 §11 territory — tests aren't optional, CI gates depend on them. A bug that silently makes 141 tests look like 0 tests would silently mean "we have no test coverage and don't know it." Fixing it permanently (not just papering over for one session) is the kind of toolchain hygiene that prevents lessons-from-the-old-bot patterns from creeping in here. Linux/CI is unaffected (chflags doesn't exist; || true swallows the error).

Task 6 — data-svc piece #3: NATSPublisher + lifespan wiring (commit eb43e3c)

Wrote services/data-svc/src/data_svc/nats_publisher.py — a small class that takes an injected nats.aio.client.Client and exposes publish_market_tick(event). The subject hierarchy follows the docstring contract in packages/bot-events/market_tick.py: events.market.tick.<exchange>.<ticker>. Publishing while the NATS client is disconnected raises RuntimeError — fail-loud, not silent drop (Lesson 8 territory). main.py lifespan extended to call nats.connect(settings.nats_url) after KalshiClient (the connect itself is a startup fail-loud probe — broker unreachable crash-loops the pod). Reverse-order shutdown: close NATS, then httpx. 3 new publisher tests + 2 new lifespan tests for the connect/close path. File-scoped pytestmark = pytest.mark.asyncio — first async unit tests in the repo.

Why it matters: v2 §05 + v2 §07 working together. data-svc now has both halves of its plumbing: it can read from Kalshi, and it can write to NATS. Nothing yet connects the two — that's piece #4 — but the wiring exists and is tested. The hierarchical subject naming (events.market.tick.<exchange>.<ticker>) means future subscribers (risk-svc, pms-svc, strategy services) can filter at the broker level. A KXPRES-only strategy subscribes events.market.tick.kalshi.KXPRES-*; pms-svc reads everything via events.market.tick.>. That subject design is permanent — every event consumer is built on top of it.

Task 7 — data-svc piece #4: tick poller (commit b821e83) — the most consequential commit of the rebuild so far

Wrote services/data-svc/src/data_svc/tick_poller.py: a background asyncio task that polls Kalshi every 5 seconds, converts each market dict into a MarketTickEvent via a defensive parser, and publishes through NATSPublisher. _market_to_event() uses .get() everywhere, catches KeyError/ValueError/TypeError/InvalidOperation/ValidationError, returns None on any failure — one malformed market never kills the loop. _poll_once() returns (published, skipped) for log accounting. tick_poll_loop() mirrors hello-svc's heartbeat pattern (try/except in body, sleep between iterations, re-raise CancelledError for clean shutdown). main.py lifespan now spawns this as an asyncio Task and cancels it under suppress(CancelledError) on shutdown.

Three design calls worth recording in this report (also in the commit message):

  1. tick_at = datetime.now(UTC), not broker time. Kalshi's /markets endpoint does not return per-market timestamps. The MarketTickEvent schema docstring previously implied broker-side time; updated to acknowledge v1 reality. Carry item: switch to Kalshi websocket (which carries server timestamps) and tick_at becomes real broker time.
  2. Markets with empty books are skipped, not emitted as Decimal("0"). Lesson 8: silent data-quality failures are how the old bot's learning system never learned. Emitting a fake 0 price would let downstream consumers treat "empty book" as "actually quoted at zero" — the kind of invisible failure the rebuild exists to prevent. Skip count is logged per cycle for observability.
  3. Volume falls back through three field names: ["volume", "volume_24h", "volume_fp"]. The legacy bot's diagnostic code defensively probed all three after empirically observing Kalshi returning different names over time. Same defensive chain here.

5 new poller tests (valid-market converter, empty-book skip, volume-fallback chain, _poll_once accounting on mixed input, clean task cancellation) + 2 new lifespan tests. Test suite: 156 passing repo-wide, zero warnings.

Why it matters: This is the first commit on Midas where a new service does something on its own. Everything before tonight was scaffolding to make this commit possible. v2 §05 (data-svc) is now actively producing events in spirit — once deployed in pieces 7/8, it will produce them in fact. The defensive parser is the architectural answer to Lesson 8: every per-market failure mode is contained, observable (skip counts logged), and never silent. The Kalshi → MarketTickEvent translation lives in the poller, not in KalshiClient — keeping KalshiClient as the low-level transport and the poller as the only code in the repo that knows both shapes. That layering will hold even as we add Polymarket later in Phase 5.

Task 8 — data-svc piece #5: Dockerfile + GHA build pipeline (commit 7b6cbc9)

Wrote services/data-svc/Dockerfile as a byte-precise mirror of services/hello-svc/Dockerfile with five line substitutions (hello-svc → data-svc, hello_svc → data_svc in the entrypoint). Multistage build: uv builder stage installs frozen deps with bytecode compile, python:3.12-slim-bookworm runtime stage drops the build toolchain, non-root app user, port 8080, uvicorn entrypoint. Wrote .github/workflows/build-data-svc.yml mirroring build-hello-svc.yml with six line substitutions (workflow name, two path filters, Dockerfile path, two image tags). Triggers on push to main when data-svc, bot-events, .dockerignore, or this workflow change. Pushes both :main (latest on branch) and :sha-<commit> (immutable per-commit) to ghcr.io/bakerlunch-ai/data-svc.

GHA run after push: success, 34 seconds. Image is in GHCR. Local Docker smoke was skipped because Docker Desktop is not installed on the dev laptop — GHA validation on Linux is functionally equivalent.

Why it matters: Closes v2 §10 for data-svc — every push to main that touches data-svc, bot-events, or the workflow file produces a tagged image in GHCR within ~3 minutes, automatically. The cluster doesn't run Python source code; it runs containers, and containers come from images. Without piece #5, the K8s manifests in piece #6 would have nothing to deploy. Now they have something. Image tagging strategy (:main mutable + :sha-XXX immutable) gives us both "latest on the branch" and "exactly what ran on day X" — the latter is what makes deploy rollback safe in piece #8 and beyond.

Task 9 — data-svc piece #6: K8s manifests for cluster deployment (commit a6ec221)

Wrote three manifests under deploy/data-svc/ mirroring hello-svc's deploy/ shape: namespace.yaml (declares data-svc namespace), deployment.yaml (Deployment manifest — 1 replica, pulls ghcr.io/bakerlunch-ai/data-svc:main, envFrom Secret kalshi-credentials, inline env vars for NATS_URL and base URL, /tmp emptyDir for cryptography's OpenSSL scratch, probes on /health:8080), and service.yaml (ClusterIP exposing port 80 → 8080 inside the cluster).

Five intentional differences from hello-svc, all documented in the commit message:

  • envFrom uses a single kalshi-credentials secret (holds both DATA_SVC_KALSHI_API_KEY_ID and DATA_SVC_KALSHI_PRIVATE_KEY_PEM), not hello-svc's [postgres-oms, redis] pair. Secret name describes contents (Kalshi creds), not consumer (data-svc) — future oms-svc or strategy services may also need them.
  • Inline env vars use DATA_SVC_ prefix per the Settings env_prefix. DATA_SVC_NATS_URL set explicitly even though Settings defaults to the same value — manifest-as-documentation.
  • Memory request bumped 128Mi → 256Mi, limit 256Mi → 512Mi. cryptography + asyncpg + redis-py + nats-py + Pydantic Decimal parsing every 5s pushes idle RSS to ~150-200Mi; 128Mi would OOM under spike.
  • /tmp emptyDir volume mounted to satisfy readOnlyRootFilesystem: true. cryptography's OpenSSL backend writes scratch to /tmp sometimes.
  • Otherwise identical security context: non-root 1000:1000, readOnlyRootFs, drop ALL caps, allowPrivilegeEscalation: false.

Explicitly NOT in this commit: deploy/applications/data-svc.yaml (the Argo Application). That ships in piece #8 specifically because the app-of-apps would auto-deploy these manifests the moment the Application file lands — and they reference a SealedSecret (kalshi-credentials) that doesn't exist yet. Piece #7 ships the secret; piece #8 ships the Application; deploy happens then.

Why it matters: v2 §07 (Kubernetes deployment manifests) for data-svc. The cluster now has, in git, a complete description of how to run data-svc: which image, which secrets, which env vars, which probes, which resource limits, which security policy. Nothing deploys yet — Argo doesn't have an Application pointing at this folder — but the deployable description exists. The deliberate sequencing (manifest → secret → Application) means deploy day is three small steps instead of one big risky one, and the failure mode at each step is contained: a bad manifest fails at git-push (YAML lint), a bad secret fails at kubeseal time (encryption error), a bad Application fails at Argo time (sync error). Each is debuggable in isolation.

04

Investigation: Phase 1.5 carry items revisited (then parked)

Mid-session we attempted to close the kps and nats OutOfSync carry items inherited from May 12. Investigation produced a sharper diagnosis than session 6's; closure deferred until DOKS cooperation improves.

kps: not a stuck PreSync hook — a DOKS apiserver flake

Session 6 framed kps as "stuck on a PreSync hook." Tonight's read of .status.operationState showed the actual failure is a transport-layer flake:

ComparisonError: Failed to load live state ... failed to load open api schema while syncing cluster cache: error getting openapi resources: Get "https://10.109.0.1:443/openapi/v2?timeout=32s": read tcp 10.108.1.90:34148->10.109.0.1:443: read: connection reset by peer - error from a previous attempt: EOF (retried 5 times)

kubectl /readyz against the apiserver passes — short requests succeed. Argo's /openapi/v2 fetch (32s timeout) drops mid-stream. This is the signature of a flaky managed control plane: healthy enough for short requests, unstable on longer ones. retryCount: 5/5 on the operation means Argo's exhausted its automatic retries. The stale syncResult message about the PreSync hook is the symptom this transport failure happened to land on, not the disease.

nats: ServerSideApply silently skipped an immutable field

Tried a kubectl-only sync (port-forward + login route blocked because the admin password has been rotated; argocd-initial-admin-secret no longer authenticates). The sync reported Succeeded with empty .status.conditions but the app immediately flipped back to OutOfSync. ServerSideApply does not error on immutable-field skips the way kubectl apply does — it just silently doesn't apply them. The actual drift is in the StatefulSet (other 6 resources Synced; only apps/StatefulSet nats/nats drifts), most likely volumeClaimTemplates which is immutable post-binding. Fix requires either ignoreDifferences on the specific path, or a --cascade=orphan recreate. Neither attempted tonight; live NATS pods have 0 restarts in 6+ days.

kube-state-metrics: 50 restarts, but past tense

Surfaced during diagnostics. Last restart 9h ago, currently Running with 0/1 readiness. Pattern timing matches the apiserver flake window exactly. Independent low-priority follow-up.

Why it matters: Tonight's investigation produced the data needed to file a real DigitalOcean support ticket (replaces the vague "apiserver seemed flaky last week" of session 6). The ticket itself was not filed tonight — a new carry item, but with concrete reproducible evidence behind it now. None of these issues block Phase 2; data-svc deploys (pieces 7/8) interact with Argo for the Application reconcile, but the underlying NATS broker and the data-svc Deployment + Service paths don't touch the failure surface.

Issues + resolutions

Issue: uv run pytest fails with ModuleNotFoundError on macOS Darwin 25

Symptom
make test errors at collection — 13 collection errors, all ModuleNotFoundError: No module named 'bot_events' / 'hello_svc'. uv pip list shows packages installed editable. Re-running uv sync doesn't fix.
Root cause + fix
All .pth files in .venv/lib/python3.12/site-packages/ had macOS UF_HIDDEN flag set. Python's site.py skips hidden .pth files silently. uv run re-hides them on every invocation. Makefile now unhides via chflags + invokes .venv/bin/pytest directly. Documented in RUNBOOK.

Issue: ServerSideApply silently skipped nats StatefulSet drift

Symptom
nats sync reports Succeeded, no error conditions, but app immediately flips back to OutOfSync. The expected immutable-field error never surfaces.
Root cause + decision
ServerSideApply doesn't error on immutable-field skips like kubectl apply does — it just silently doesn't apply. Drift will persist until we either patch ignoreDifferences on the specific path, or recreate the StatefulSet with --cascade=orphan. Neither attempted tonight; live NATS pods 0 restarts 6+ days; deferred.

Issue: argocd CLI login fails — admin password rotated

Symptom
argocd login localhost:8080 fails authenticating with argocd-initial-admin-secret. New admin password lives only in Filippo's password manager (not in any cluster secret).
Decision
Switched to kubectl-only path (no argocd CLI, no port-forward, no password in chat). All sync operations done via kubectl annotate refresh=hard or kubectl patch ... operation. Carry items: stale argocd-initial-admin-secret should be deleted; admin-password rotation should be noted in RUNBOOK.

Issue: Pydantic ValidationError on first NATSPublisher test run

Symptom
_sample_tick() helper used wrong field names against real MarketTickEvent schema — used observed_at (real field is tick_at); missing emitted_by, exchange, volume_24h, open_interest; prices in 0.0-1.0 range (real schema is 0-100 cents).
Fix
Read canonical constructor from packages/bot-events/tests/test_market_tick.py::_valid_kwargs — the existing proven-valid test setup. Rewrote helper to mirror exact field names + cents convention. Also surfaced that the schema docstring says subjects should be events.market.tick.<exchange>.<ticker>; updated NATSPublisher to use that hierarchical form.
