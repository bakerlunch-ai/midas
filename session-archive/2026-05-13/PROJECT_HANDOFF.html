01

What Midas is

Midas is a from-scratch rebuild of a Kalshi prediction-market trading bot. The previous bot (audited April 2026, paused) reached ~5,300 lines in one Python file with multiple structural bugs (bankroll only goes up, dead reconciliation, dead strategies, magic numbers everywhere). The audit synthesis documented those failures; the architecture v2 document committed to a multi-service event-driven system inspired by hedge-fund OMS/EMS/Risk separation.

Midas is being built deliberately, slowly, and well — explicitly avoiding the patterns that broke the old bot. The 10 lessons from docs/LESSONS_FROM_OLD_BOT.md are binding constraints, not suggestions.

Eventual architecture (target state, not current)

  • data-svc — ingest market data, FRED, news, Claude AI edge analysis (currently 6/8 pieces built, none deployed yet)
  • strategy-* services — one per strategy (TIMELY, MIDSEL, ARB, etc.), independent deploys
  • risk-svc — single point for all risk gates and Kelly sizing
  • oms-svc — order lifecycle, event-sourced ledger, daily reconciliation
  • ems-svc — execution against venues, two modes: live and paper
  • pms-svc — positions, P&L, bankroll, event-sourced
  • reporting-svc — dashboards and reports
  • telegram-svc — human interface (alerts, commands)
  • mcp-svc — exposes the bot as an MCP-compatible server for AI agents

All services communicate via NATS JetStream. Two PostgreSQL event-sourced ledgers (orders, portfolio). LGTM observability stack (Loki, Grafana, Tempo, Prometheus). Managed Kubernetes on DigitalOcean (DOKS).

03

The infrastructure stack, in plain English

This is a primer on every piece of software in the Midas stack — what each one is, what it does, how they talk to each other. Written for a reader who doesn't live in this world day-to-day. The kitchen analogy from Section 02 anchors throughout: the restaurant is Midas, the building is the cluster, the chefs are the services.

The big picture in one paragraph

We write Python code on our laptops. uv manages the Python dependencies. Git tracks our code; GitHub hosts the repo and runs automated builds via GitHub Actions. Those builds produce Docker images — frozen-meal-style packages of our code plus everything it needs to run — and push them to GHCR (GitHub's image warehouse). Meanwhile, DigitalOcean rents us a small computer farm running Kubernetes (DOKS), which is the operating system that decides which images run on which farm computers. Argo CD is the foreman of the farm — it watches our git repo, sees new YAML files describing what should run, and tells Kubernetes "go pull this image from GHCR and run it." Sealed-secrets lets us put encrypted passwords in git so Argo can read them but humans browsing git can't. Once services are running, they talk to each other through NATS (an in-cluster message bus). They store permanent records in PostgreSQL and fast-but-forgettable state in Redis/Valkey. They emit logs to Loki, metrics to Prometheus, distributed traces to Tempo, all viewable through Grafana dashboards. The shipper that gets logs into Loki is called Alloy. The services themselves are built with FastAPI + Pydantic. Claude Code is the AI pair-programmer Peter operates from his terminal.

Now the pieces, one by one

The farm

DigitalOcean (DO)

The cloud provider — they rent us the underlying computers. Same way you'd rent an apartment instead of buying a house. We use DigitalOcean Kubernetes Service (DOKS) which is their managed Kubernetes offering: they handle the control plane (the "operating system" of the cluster), we just rent the worker nodes that actually run our code. Total cost: ~$130/month. They also host our managed PostgreSQL and managed Redis (we don't run these ourselves — DO operates them, we just connect to them over their private network).

Kitchen analogy: DO is the landlord. We don't own the building. We pay rent, get keys, and walk in to do our work.

The traffic cop

Kubernetes (k8s)

An open-source system that orchestrates containers (think: which copies of which programs run on which farm computers, restarts them when they crash, spreads them out for resilience). Kubernetes is the most-deployed orchestrator in the world. You describe what you want with YAML files — "run 1 copy of data-svc with this image, give it 256MB memory, restart it if it dies" — and Kubernetes figures out the rest. DOKS is just "Kubernetes that DigitalOcean operates for us."

Kitchen analogy: Kubernetes is the head chef who decides which station each cook works at, what their break schedule is, and who to bring in if someone calls out sick. We don't tell each cook where to stand; we tell the head chef "I need 1 prep cook tonight" and trust them to handle staffing.

The frozen meal

Docker image (and "container")

An image is a snapshot of our Python code, all its dependencies (cryptography, FastAPI, etc.), and a thin Linux environment around it — bundled into one ~200-250MB file. You build the image once, and any computer with Docker installed can "thaw" it (run a container from it) and get the same predictable behavior. The image for data-svc is at ghcr.io/bakerlunch-ai/data-svc:main. A "container" is just a running instance of an image — like a single bowl of soup made from the frozen recipe.

Kitchen analogy: An image is a frozen meal box from the freezer, the recipe printed on the side. A container is when you actually heat one up and serve it.

The freezer aisle

GHCR (GitHub Container Registry)

The warehouse where our Docker images live. When GitHub Actions builds an image, it pushes the finished image to GHCR under ghcr.io/bakerlunch-ai/<service-name>. Argo CD later tells Kubernetes to pull from this address. GHCR is built into GitHub — no separate account needed. Images can be tagged :main (the latest build on the main branch) and :sha-abc123 (the exact build for that specific git commit, never overwritten).

Kitchen analogy: GHCR is the freezer aisle of the grocery store. Each shelf has a label (the tag). When you cook tonight, you grab a frozen meal by its label — could be "latest version" or "the one from exactly two weeks ago."

The foreman

Argo CD (the GitOps engine)

A program running inside our cluster whose only job is: watch our git repo, see what YAML files say "this should be running," and make the cluster match. If you push a new manifest to git that says "run 2 copies of data-svc," within ~3 minutes Argo notices, pulls the image, and tells Kubernetes to run it. Argo provides a web dashboard showing the sync status of every "Application" — an Application is Argo's name for "a thing we're deploying." Tonight we have 9 of them: alloy, app-of-apps (the parent that auto-creates the others), hello-svc, hello-world, kube-prometheus-stack, loki, nats, sealed-secrets, tempo. Two are currently OutOfSync but functional (kps and nats — see carry items).

Kitchen analogy: Argo is the foreman who checks the supplies manifest every morning and rearranges the kitchen to match. "Recipe says we need 3 burners on tonight — yesterday we had 2, so I'll fire up another." We never directly touch the kitchen layout; we just edit the manifest.

The locked pantry

sealed-secrets

Passwords in git are obviously a bad idea — anyone with read access to the repo would see them. Sealed-secrets solves this. We take a regular Kubernetes Secret (which holds, say, the Kalshi API key), encrypt it with a public key the cluster published, and commit the encrypted blob to git. Only the cluster (which has the matching private key) can decrypt it. Argo applies the encrypted blob; the cluster decrypts; the running pod sees the plain-text value via an env var. Humans browsing git see only ciphertext.

Kitchen analogy: The pantry has a special padlock. Recipes (in git) can reference "ingredient #4 from the pantry" without saying what it is. Only the pantry-key (held by the kitchen, not in any cookbook) can open the lock. Cooks get the ingredient when they're working a shift; bystanders never see it.

The intercom

NATS JetStream

The in-cluster message bus that services use to talk to each other. Instead of data-svc making an HTTP request to risk-svc directly (which would couple them tightly), data-svc publishes a message to a subject like events.market.tick.kalshi.PRES-2028-DEM, and any service that subscribed to that subject receives the message asynchronously. If risk-svc is offline for an hour, NATS holds the messages and delivers them when risk-svc comes back. JetStream is NATS's persistence layer — durable subscriptions so we don't lose events on broker restarts.

Subject hierarchies enable selective fanout: events.market.tick.> means "every market tick"; events.market.tick.kalshi.> means "every Kalshi tick"; events.market.tick.kalshi.KXPRES-* means "every KXPRES Kalshi tick." Subscribers filter at the broker, not in app code.

Kitchen analogy: NATS is the kitchen intercom system. The prep cook (data-svc) calls out "TICKERS UP" to the whole kitchen. Cooks who care about tickers (risk-svc, strategy-svc) hear it and act; cooks who don't (reporting-svc maybe) ignore it. The prep cook doesn't need to know who's listening.

The ledger book

PostgreSQL (Postgres)

The relational database where we store permanent records. Three logical databases on one managed Postgres cluster: oms_db (order management — every order placed, filled, cancelled), pms_db (portfolio management — positions, P&L, bankroll over time), reporting_db (analytics). Both oms_db and pms_db will be event-sourced — instead of storing "the current bankroll is $400," we store every BankrollChangedEvent ever and compute the current bankroll by replaying them. This is one of the binding constraints from the old bot's audit (Lesson 1: bankroll only goes up).

Kitchen analogy: The handwritten ledger book that records every transaction since the restaurant opened. You can flip back and reconstruct any past state. We never erase entries; we only add new ones.

The whiteboard

Redis / Valkey

A fast in-memory cache. We use DigitalOcean's managed Valkey (a Redis-compatible fork). Stores ephemeral state — rate-limit counters, short-lived auth tokens, session-like data. If Redis loses everything in a crash, we lose nothing important; Postgres has the durable record.

Kitchen analogy: The whiteboard near the pass where the line cook scribbles "ticket 47 needs the burger now" or "we're out of avocado til 6pm." Erased and rewritten constantly. Nothing on it would be missed if the whiteboard fell off the wall.

The CCTV system

LGTM observability stack: Loki + Grafana + Tempo + Prometheus + Alloy

Five tools working together to make the cluster observable. They have overlapping names so people refer to them as "the LGTM stack" — Loki, Grafana, Tempo, Metrics (Prometheus).

  • Loki — stores logs. Every line of stdout from every pod ends up here, queryable by service name, namespace, time range.
  • Prometheus — stores metrics. Numbers over time: how many requests per second, how much memory each pod is using, error rates. Prometheus periodically scrapes endpoints exposed by each service.
  • Tempo — stores distributed traces. When one event flows through 4 services (data → risk → oms → ems), Tempo lets us see the whole path as a single trace.
  • Grafana — the dashboards. The pane of glass that queries Loki, Prometheus, and Tempo and shows you what's happening. This is the only one humans look at directly.
  • Alloy — the log shipper. Runs on every node, tails pod stdout, ships it to Loki. Shipped in session 6 to close Phase 1.5 problem #2.

Kitchen analogy: The CCTV system. Loki is the room that stores all the audio recordings (logs). Prometheus stores all the temperature readings off the kitchen thermometers (metrics). Tempo stores the videos that follow a single order from receipt to delivery (traces). Grafana is the monitor at the manager's desk where they can watch any of it. Alloy is the microphone array in each room — picks up everything and sends it to the recording room.

The recipe books

GitHub + GitHub Actions

GitHub hosts our git repository — the source of truth for code, manifests, docs, everything. GitHub Actions is GitHub's built-in automation: every push to main can trigger workflows (recipes) that GitHub runs on their own Linux servers. Our workflows do two things: (1) ci.yml runs make install && make lint && make test to make sure nothing broken reaches main, and (2) build-data-svc.yml (added tonight) builds the Docker image and pushes to GHCR whenever the service code or its build files change. Each Actions run is logged and visible in the GitHub web UI.

Kitchen analogy: GitHub is the cookbook library. Actions are the test-kitchen team that, every time a recipe changes, cooks it once to verify it still works, and stocks the freezer aisle (GHCR) with a fresh batch.

The dependency manager

uv (Python tooling)

A fast Python package manager + virtualenv tool, written in Rust, that replaces pip + virtualenv + Poetry. We use it for everything: installing dependencies, running tests in isolated envs, building wheels. uv sync --all-packages installs every workspace package; make test uses uv under the hood. Has one known macOS-specific quirk we worked around in session 7 (the UF_HIDDEN bug on editable-install .pth files).

Kitchen analogy: The dishwasher and prep tools. Behind the scenes, makes sure every workstation has clean equipment ready before service starts.

The schema language

Pydantic + FastAPI

Pydantic is a Python library for declaring data structures that validate themselves. MarketTickEvent is a Pydantic model — declares which fields it has, their types, their constraints (price must be 0-100 cents, volume must be ≥0, etc.). At runtime, constructing an instance with bad data raises ValidationError. We use Pydantic for every event in bot-events, for service settings (env-var validation), and for HTTP request/response bodies. FastAPI is the web framework that builds on Pydantic — when you write a FastAPI endpoint, the function signature itself becomes the contract.

Kitchen analogy: Pydantic is the order-ticket validation: the ticket says "burger, medium-rare, no onion" and the validator refuses tickets that say "burger, blue, with quantum onions." Catches bad orders before they reach the cook.

The pair-programmer

Claude Code

An Anthropic CLI tool Peter operates from his terminal. Reads files, edits files, runs commands. Operates inside Filippo's chat context — Filippo asks Claude (this chat) what to do, Claude writes prompts for Claude Code, Peter pastes them, Claude Code does the actual file/git/build work. The pattern is "two Claudes": one is the strategist (this chat), one is the actor (Claude Code). They never talk directly; the human pastes between them.

Kitchen analogy: Claude Code is the sous chef who can execute any prompted task in the kitchen — chop, sear, plate — but waits for direction. The Claude in this chat is the executive chef who plans the menu and explains why each dish matters.

How a single market tick flows through the system (concrete example)

Once piece 7 + piece 8 land and data-svc is deployed, this is what happens when Kalshi's API has a price update:

  1. Every 5 seconds, data-svc's tick_poll_loop wakes up inside its pod (running on a DOKS worker node).
  2. data-svc calls GET /trade-api/v2/markets on Kalshi, authenticating with the API key + RSA-signed request. The credentials come from the sealed-secret kalshi-credentials, which Argo decrypted when it deployed the pod.
  3. Kalshi returns a JSON list of markets. data-svc parses each one (defensively, with .get() everywhere) and builds a MarketTickEvent. Markets with empty books are skipped; the skip count is logged.
  4. For each valid market, data-svc calls publisher.publish_market_tick(event), which serializes via Pydantic's .model_dump_json() and publishes to NATS subject events.market.tick.kalshi.<ticker>.
  5. NATS holds the message. No subscribers yet — that's fine, NATS just keeps it.
  6. Meanwhile, stdout from data-svc's poll loop — including the "published=42 skipped=3" line — is captured by the Alloy DaemonSet on the same node and shipped to Loki.
  7. If you open Grafana and query Loki for {namespace="data-svc"} you see those lines live. Eventually we'll add a Tempo trace from the publish, but tonight that's not wired up.

Later, when risk-svc and strategy-svc come online (Phase 3), they'll subscribe to events.market.tick.kalshi.> and receive these messages automatically. data-svc never has to know they exist.

07

Decisions on record (must not relitigate)

  • NATS subject naming: events.market.tick.<exchange>.<ticker>. Hierarchical, broker-side filterable. Permanent.
  • Service Settings env_prefix: each service uses its own prefix (e.g. DATA_SVC_). Prevents accidental cross-service env-var leakage.
  • FastAPI lifespan owns connection lifecycle: resources (httpx, NATS, future Postgres/Redis) are constructed in lifespan and closure-captured, not on app.state.
  • Fail-loud startup probes: each service's lifespan runs a one-shot probe (Kalshi auth, NATS connect). Failure crash-loops the pod immediately.
  • Defensive parsing of external data: .get() everywhere, catch broad exception families, skip bad records with logged counts. Never silent-emit zeros or fabricated values.
  • Tick prices in cents (0-100), not probabilities (0-1): Kalshi convention. Decimal type. Pydantic validates range.
  • Async tests use file-scoped pytestmark = pytest.mark.asyncio: precedent set in test_nats_publisher.py.
  • K8s manifests live at repo root deploy/<service>/, Argo Applications at deploy/applications/, sealed-secrets at deploy/secrets/<service>/.
  • Secrets named by contents, not consumer: e.g. kalshi-credentials not data-svc-kalshi. Future services may share.
  • readOnlyRootFilesystem: true on every service pod; emptyDir mount at /tmp when the runtime (e.g. cryptography) needs writable scratch.
  • Skip local Docker smoke when Docker Desktop absent; trust GHA Linux build as functional equivalent.
  • tick_at = datetime.now(UTC) for poll-mode v1: /markets has no broker timestamp. Carry to websocket migration.
